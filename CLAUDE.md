# CLAUDE.md

Context for Claude about the Mitts project. Deep technical reference (networking invariants, class-boundary detail, backlog) lives in `ARCHITECTURE.md`.

## Workflow

Complex features (AI state machines, new systems, architectural changes) can be designed first in Claude.ai chat mode, where the developer can iterate on ideas without implementation pressure. The resulting plan is then handed to Claude Code to implement against the actual codebase. When a session starts with a plan document, treat it as the agreed design — ask clarifying questions before deviating from it.

**Never push to `main` without the user testing locally first.** Feature branches (e.g. `claude/*`) may be pushed after committing so the user can pull and test on their machine. Merging a feature branch into `main` is done by the user via a pull request in the UI — do not `git merge` a feature branch into `main` directly. For work done directly on `main`, always stop at commit and wait for explicit confirmation before running `git push`.

**Scene files (`.tscn`) and complex resource files (`.tres`) are edited by the user, not Claude.** Godot's text formats are error-prone to edit when they contain node unique IDs, sub-resource references, or property ordering that the editor enforces — multi-node scenes, themes, shader materials, animations, etc. Describe the change and let the user make it in the Godot editor. **Trivial single-resource `.tres` files (e.g. `PhysicsMaterial`, simple `StandardMaterial3D`) are safe to author directly** — they're 3-5 lines with no cross-references. The UID line is optional; Godot generates one on first import if omitted.

**You can run the GUT test suite headless; you cannot run the game.** Use the `.claude/hooks/run-gut.sh` runner (it invokes `godot --headless -s res://addons/gut/gut_cmdln.gd`, honoring `.gutconfig.json`). Pass `gut_cmdln` flags through, e.g. `-gdir=res://tests/unit/state`.
- **Local:** `GODOT_BIN` (set in `.claude/settings.local.json`) points at the Godot executable. Full suite ≈ 15–18s. **Redirect to a file, don't pipe** — the Windows console exe throttles badly on an MSYS pipe (≈90s vs ≈18s): `bash .claude/hooks/run-gut.sh > "$TMP/gut.log" 2>&1; tail -40 "$TMP/gut.log"`.
- **Web (Claude Code on the web):** the `SessionStart` hook (`session-start.sh`) async-installs Godot; run `.claude/hooks/wait-for-godot.sh` once before the first test run, then `.claude/hooks/run-gut.sh` (piping is fine on Linux).

Run the suite after touching domain code and report results. **AI perf changes additionally run the benchmarks** (`bash .claude/hooks/run-gut.sh -gdir=res://benchmarks` — report-only host-cost scenarios + per-evaluator micro-bench, outside the default suite): compare the before/after tables, especially per-tick p95/max (host FPS is set by the worst tick) and the per-call evaluator ranking. The **game itself** still can't run here (needs a display / interactive session) — for gameplay or networking changes, describe what to test in a local session and wait for the user to verify.

**Warnings: run gdlint before committing `.gd` changes.** `.claude/hooks/run-lint.sh` runs `gdtoolkit`'s gdlint (tuned via `.gdlintrc`) — the headless, cross-environment subset of warnings: dead code, unused args/vars, `duplicated-load`, trailing whitespace. A committed `.githooks/pre-commit` gate (activated via `core.hooksPath`, set locally and by the SessionStart hook) **blocks any commit with gdlint problems in staged `.gd` files** (`--no-verify` to bypass). Keep the tree gdlint-clean. Caveat: gdlint can't see Godot's *engine-specific* analyzer warnings (`SHADOWED_VARIABLE_BASE_CLASS`, `INT_AS_ENUM`, narrowing) — those remain editor-only, so a clean gdlint run isn't a guarantee the editor is warning-free.

**If you spot a bug or code smell while working on something else, flag it.** Don't silently fix it (out of scope), don't silently ignore it (it'll rot), don't tack it onto the current commit (muddies the diff). Surface it in chat with a one-line description and let the user decide: fix now as a small follow-up, defer to a separate task, or capture as a Known Issue here. Latent bugs in adjacent code paths are especially worth flagging — they often pair with whatever you're touching.

**Stale documentation is the exception: fix it on the spot.** When a doc or comment (this file, `ARCHITECTURE.md`, doc-blocks, constant tables) no longer matches the code, correct it as part of whatever you're doing — don't flag it as out of scope, don't ask. Keeping documentation and comments truthful is always in scope; a stale doc found while working nearby goes into the same commit.

## What This Is

A 3v3/5v5 hockey game built in Godot 4.6.2 (GDScript, 3D). Online multiplayer — one player per machine, each with their own camera and local simulation. Prioritizes feel over realism: deep stickhandling, multiple shot types, satisfying puck physics. 3v3 (position-free rovers) is the default mode; **5v5** is lobby-selectable and adds the forward/defense split — full design in `docs/5v5-ai-plan.md`.

**The puck is a plain `Node3D` — no physics body on any peer.** The deterministic analytic sim is the only puck simulation: the host drives it (`Puck._drive_analytic`), clients predict with the literally-shared step (`PuckAuthorityRules.step_frame_substep`), and every contact (boards, goal frame, goalie, blades, bodies) is analytic. Do not suggest CCD, contact monitors, or any physics-body fix — there is no body. Tunnelling is handled by the step's near-frame sub-stepping, and containment is by construction (the step clamps the center to `GameRules.clamp_to_rink_inner` every sub-step), so a puck outside the rink means either a >2 m single-tick teleport (deliberate drill staging) or a solver bug — check the `[puck-oob]` whistle diagnostics.

## How It Plays

**Mouse + keyboard and gamepad are both first-class; which one drives is pure last-input-wins** — there is **no opt-in flag and no mode switch**. `InputDeviceTracker` (autoload) tracks the CURRENTLY-driving device: touch the mouse and it drives, push the stick and the pad takes over, with switch thresholds set above the gameplay deadzones (`_STICK_SWITCH_DEADZONE` 0.5 vs. aim/move ~0.15) so a resting/drifting stick never steals control. `InputDeviceTracker.is_gamepad_active()` is the single source of truth every device-facing surface reads — so a mouse player who never touches a plugged-in pad is simply always KBM and sees zero gamepad UI, and a Steam Deck player just uses the pad and everything works, no setting to find. The one setting is an accessibility OFF switch (Options → Controls, "Keyboard/Mouse Only" → `PlayerPrefs.disable_gamepad`, off by default): it pins `is_gamepad_active()` false so a drifting/unwanted controller that can't be unplugged is ignored entirely (Options apply calls `InputDeviceTracker.notify_gate_changed()` so the flip reaches the device-aware UI without new input). **Control, prompts, and focus rings all stay linked** because they all key off that one flag:
- **Control**: `LocalInputGatherer._gamepad_active()` and the spectator free cam branch on `is_gamepad_active()`.
- **Prompt glyphs** (`ControllerGlyphs.prompt`): the persistent hints (the HUD menu-open + skip-vote prompts, the side-menu close hint) rebuild on `InputDeviceTracker.device_changed`, so pressing the mouse flips them to keyboard labels and pushing the stick flips them to pad glyphs; the **tutorial's teaching prose** does the same (`_pick` / `_build_key_tokens` read `is_gamepad_active()`, and it re-emits the current step on `device_changed`).
- **Menu focus rings**: the tracker owns ONE shared focus-ring stylebox (`InputDeviceTracker.focus_ring()`, handed out by `MenuStyle.apply_focus_ring` / `controller_focus_theme`) that goes teal while the pad drives and zero-width/invisible the instant the mouse does. So controls can be focusable unconditionally and a mouse click still shows no ring; `ControllerNav.active()` (which gates whether focus is *grabbed*) is `is_gamepad_active()`. `boot.gd` focuses Play at build so a pad player's first button press activates it, and the device-aware ring keeps that focus invisible for a mouse player.

Device *arbitration* is a purely local, presentation-time concern — which device drives decides how the local `InputState` gets *populated* (OS mouse vs. synthesized-from-stick), and no peer needs to know which one you used. That does **not** mean the pad path is netcode-free: the committed wrister power it produces is a real replicated input field (see the wrister bullet below), because a parked pad cursor gives the host nothing to re-derive power from. Treat "which device" as local and "what the device committed" as wire. WASD skates, mouse cursor places the blade in real-time (continuous IK — the blade chases the cursor every frame, no aim button). When the pad is the active device, `LocalInputGatherer` swaps the aim source: the right stick becomes an absolute "skill stick" (`GamepadAimRules`) that synthesizes a screen cursor into the same `InputState.mouse_screen_pos`/`mouse_world_pos` the mouse feeds, so blade IK runs unchanged (left stick skates, the pad's buttons map onto the existing action flags). Stickhandling maps the stick to an absolute blade offset (easing to a forward carry rest on release); the **wrister** is a *committed* shot rather than the mouse's flick — while RT is held the cursor parks in the stick direction **anchored on the puck, pinned at the trigger edge** (`_pin_shot_anchor` / `_shot_anchor_screen`, NOT the body and NOT a live blade read: the aim is positional origin→cursor from that same puck, so a body-anchored cursor made the shot line the stick direction *parallel-shifted by the ~1 m carry offset* — a ~4°–15° bias that flipped with carry side and rode the dynamic zoom — while a live blade anchor would swing the line as the skater carried the blade away from the pinned origin. Pinning at the edge makes stick direction = shot line by construction, at any zoom, for the whole hold — and it's what lets the swing-chirality hand read work on a pad) and the stick push magnitude commits the power fraction (`InputState.commit_wrister_power` → the same `bot_wrister_power_t` path bots use, *replacing* the cursor-speed read since a parked cursor has ~0 speed), so a controller shot is "point the stick, push harder for more power, release to fire" with no flick timing. Both the aim and the power latch **hold on a centered stick** (a stick inside the deadzone carries neither signal, so the thumb coming home can't collapse a lined-up shot to the 10 m/s floor), and the latch **seeds full at the trigger edge** so a bare RT with no stick input is a rip along the held aim rather than the softest shot in the game. (`commit_wrister_power` + the power fraction are **on the wire** as of `PROTOCOL_VERSION` v41 — flag bit [13] plus a u8, so an online pad client's shot power reaches the host instead of the host re-deriving it from the parked cursor and firing a floater. The gatherer quantizes to the wire grid at the *source* (`InputState.quantize_power_t`) so local prediction and the host match bit-exactly.) Camera is third-person, per-player, dynamic-zoom, tilted ~75° so cursor-to-world projection stays usable for stickhandling.

**Stickhandling is physical, not abstract.** The puck is a real simulated disc that attaches to the blade by proximity; there is no possession flag you press to engage. Carrying slows you. Moving the cursor swings the blade through forehand/backhand with a small lift through center — that's the "dangling" texture. Hard incoming pucks (above `deflect_min_speed`, 22 m/s **receiver-relative**) deflect off a poorly-angled blade; passes (snap ~14, AI feeds solved to arrive at 20 m/s *in the receiver's frame* — `AIActionScoring.PASS_TARGET_CLOSING_M_S` — soft-sweep wristers down to ~10) catch at any angle for a static or retreating receiver. Reception is purely reactive — it reads the puck's speed **in the receiver's frame** (puck velocity − skater velocity) and the blade angle at contact, nothing else — so a stretch pass to a streaking receiver arrives soft (easy catch), charging head-on into the same feed steepens it past catchable, and skating backward with a hard shot cushions it under the ceiling ("give with the puck" as a *skating* read). Squaring the blade to the relative incoming line is what lets you corral a harder shot (the `alignment_receive_bonus` ceiling, 30 m/s relative); there is deliberately no blade-velocity cushion term (it rewarded a preemptive backswing that felt fiddly — the frame correction rewards positioning, not stick wind-up). The 22/30 thresholds are calibrated to real reception — pros routinely handle ~45–50 mph feeds and treat ~60+ mph as a knock-down even squared; force math + sources on `PuckReceptionRules.should_receive`. Above that ceiling the contact is a **deflect**, and the deflect physics itself produces the whole spectrum from a **bobble** (you knocked it down, it dies in front — a squared blade smothering a hard shot) to a **live redirect** (a glancing blade tips the puck off its line at near-full pace — the deflection-goal geometry). **Hold Q (Deflect) without the puck to deliberately deflect** — a committed "redirect this, don't catch it" that tips even an otherwise-catchable puck off the blade face (angle the blade with the cursor to aim the redirect); release to receive normally. The **loft level (scroll)** picks the deflection *intent* rather than a launch height (a monotonic "higher = launch higher" would rocket a hard tip over the net), and the three levels are symmetric about the ice: **FLAT** keeps a grounded puck low (redirect along the ice); **LOW** takes a grounded puck **up** (the money tip — lift a low shot up and in); **HIGH** raises the blade into the air, where the redirect direction stops being a choice and becomes **geometry** — the blade bats **down** what it sits above and lifts **up** what it sits under (`PuckCollisionRules.deflect_loft_speed`), so getting under a puck is what roofs it. That's the airborne tip-in, and it's a *positioning* read, not an aim: a HIGH feed arrives at a net-front player around 0.9–1.1 m, and a lifted blade pivots at 0.55 m and reaches to ~1.05, so where you stand along the arc picks the outcome. Camping HIGH can't cheese saucer passes, because a saucer apexes at ~0.26 — far below the pivot — so it's always a knock-down; getting *above* the pivot means the puck is genuinely high. The raised HIGH blade is also what hooks under an opponent's shaft, so **stick-lift is the same gesture** (hold Q at HIGH near a carrier's stick). Reach follows the blade plane (FLAT/LOW play the ice, HIGH plays the air — an airborne puck flies over a FLAT/LOW blade, a grounded puck passes under a HIGH one); the level picks which plane you play, and on the ice it also names the direction. Deliberate and natural deflects run the *same* physics (`PuckCollisionRules.deflect_velocity`), so they always feel identical — one **normal/tangential decomposition** of the incoming velocity against the blade face (the into-face component rebounds with a speed-dependent restitution so hard pucks die head-on; the along-face glance is kept, so a tip holds its pace), with bobble/redirect emerging from blade angle alone and the loft level signing the redirect (flat / up / down). Tunables (`deflect_*`, `bobble_*`) live on `Puck` (detail in ARCHITECTURE → Puck Interactions). AI bots don't use deliberate deflect or voluntary lift (their one-timers hold the slapshot charge off-puck — the real one-timer mechanic, wind-up and all); Q off-puck for a human is deflect, tapped-on-puck it's still the nudge. No `deke` button — deception is blade placement plus skating rhythm.

**Three fire inputs, all aim-aware** (the quick pass, plus two real shots):
- **Quick pass** (E, rebindable) — fires *instantly* from carry (no aim state), a fixed-power blade→cursor snap toward the cursor. This is the **pass**, not a viable shot — its power is flat pass speed for everyone. Aim is blade→cursor (from the puck's position toward the cursor, so it goes where you point); it deliberately does *not* aim player→blade, which used to inherit the blade's lateral carry-side offset and pull the pass off the cursor line. It's on its own button so there's no tap-vs-hold guess: originally the quick pass and wrister shared LMB and were split by a ~60 ms hold-time cutoff, but an ordinary tap that lingered a few ticks fired a wrister when the player wanted a snap pass. AI bots fire it via the `quick_pass_pressed` input flag (their uncharged pass). (Internally the button/action/flag are all `quick_pass*`; older history called it "quick shot" — it is a pass, treat it as one.)
- **Wrister** (LMB) — a **coil-and-release**: LMB-down FREEZES the blade+puck at the shot origin (the puck sits *still* where it'll fire from — a legible "committing to a shot" tell for the goalie and other players) while the torso **coils** toward the cursor; releasing fires **instantly** along **origin→cursor** — the *positional* aim ("the puck fires from where it sits toward where you point"), the SAME aim the quick pass uses, so a quick pass is just a fixed-power wrister and the two no longer fight (the old drag-vector aim is gone — it conflicted with the quick pass and couldn't be previewed). The origin (`SkaterAimingBehavior.wrister_origin_world`) is pinned at charge start and reconcile-restored like the rest of the charge state. Power is unchanged: the **pure mouse-speed model** (`ShotMechanics.wrister_power_t`) — raw screen-space cursor speed at release, scaled by **Shot Power Sensitivity** (DPI-independent), feel-curve exponent (`wrister_power_curve`); slow sweep = soft touch pass (floor ~10 m/s), hard flick = ~33 m/s Shot-scaled ceiling. Forehand/backhand is the **cursor's bearing-sweep chirality** (`ShotMechanics.is_backhand_from_swing`; the blade is frozen, so the cursor is the only sweep — a straight drag defaults forehand via `wrister_backhand_deadband`). The clockwise check runs on the **shot line, origin→cursor** — the same vector the release fires along — **not** on a body-relative bearing: measured about the body it would also rotate with the ~1 m blade parallax, banking swing the player never gestured. That one anchor choice is what makes the read device-agnostic — a mouse sweeps the shot line by moving the cursor, a pad by rotating the stick (whose cursor is anchored on the puck, so stick bearing *is* the shot line's bearing) — so there is no per-device hand branch. The **blade-travel power gate is DORMANT** (`ShotMechanics.wrister_travel_cap_t`, `wrister_full_stroke_travel`): a frozen blade banks no blade path, so `_wrister_stroke_travel` returns INF and power is uncapped mouse-speed (twitch = max for now) — the mechanism is kept as the hook for a future **cursor-sweep** anti-degeneracy gate. `shot_charge` still carries normalized release-now power (the goalie's pre-lean + the stick-flex pose read it); no on-screen charge ring. **Release → follow-through is an explosive, arm-controlled "whip"** (`SkaterShotPoseCoordinator._apply_wrister_whip`): the blade drives forward *along the shot line from the body* (`ShotMechanics.whip_local_dir` keeps it on the shot vector as the torso rotates — never radial, and the arm can't stretch because it's the hand carry, not a blade anchor), on an **attack-hold-release** envelope (`wrister_whip_attack_frac`/`_release_frac`) so it snaps to the extended finish and holds; the torso **through-overshoot is direct-driven** (discharges *with* the release, no lerp lag that read as delay), facing **re-squares hard** through the finish (`follow_through_facing_recover_speed` — the coil freezes facing at the wind-up cursor, so without this the blade hands back to cursor-tracking by swinging to the stale-facing side), and the **legs kick** (`SkaterSkatingCoordinator`, powered by the actual release charge so a hard flick kicks hard). Tunables (`wrister_mouse_speed_full`, `wrister_mouse_speed_smoothing`, `wrister_power_curve`, `wrister_backhand_deadband`, `wrister_follow_through_*`, `wrister_whip_*`, `follow_through_*` incl. `follow_through_facing_recover_speed`) on `SkaterController`; `wrister_power_curve`'s default is shared with bots via `GameRules`. **Bots have no cursor, so they COMMIT their intent directly** (the same seam that already commits power): aim direction, hand, and power via `InputState.bot_wrister_aim_dir` / `bot_wrister_backhand` / `bot_wrister_power_t`, set in the agent's shoot/charged-pass states — the exact shot the scorer evaluated (`release_pos → aim_point`, execution error folded in). The controller uses the commits for bots (`_wrister_aim_dir` / `_wrister_is_backhand`) and positional/sweep for humans; the bot's synthesized cursor is now purely the cosmetic wind-up coil (it no longer drives aim or chirality). Real puck, real stickhandling, real physics — only the input layer is synthesized.
- **Slapshot** (RMB) — time-charged wind-up, aim locked at press. Charge feedback is **fully diegetic**: the wind-up animation (blade lift, torso coil, stick rising to `slapper_wind_up_height`) fills over the same `max_slapper_charge_time` as the charge itself — the pose IS the gauge — with a small blade quiver at the apex as the full-charge tell (`slapper_full_quiver_*`); there is no charge ring. Supports **one-timers**: charge without the puck, release fires when the puck enters the shooting zone, at whatever charge was actually built (plus the `one_timer_center_power_bonus` timing bonus) — winding up early is what buys a full-power one-timer. The locked aim is **blade→cursor** for humans; **bots commit the direction** (`InputState.bot_slapper_aim_dir`, the same seam as the wrister's `bot_wrister_aim_dir`) since they can't reconstruct the blade's world anchor from a snapshot — the one-timer is their only slapper, and it commits the settled release point → the scored net hole.

Backhand shots take a power penalty. Scroll wheel steps a three-level **loft mode** (flat / low / high) that applies to every release in every direction. Each level is a fixed *vertical launch speed*, not a solved arc: LOW is a saucer flip (~0.26 m apex — clears stick blades, lands and slides), HIGH peaks ~1.12 m (puck top ~1.14 m — a clean ~5 cm under the crossbar's inner edge, so you can snipe the top of the net but not sail it over; apex is a fixed height ceiling, power only moves the apex *distance*). Charge buys pace, loft buys height, and where the arc sits when it reaches the net is emergent from distance + power — that range/charge read is the top-corner skill. Passes are quick passes — same mechanic, no separate pass system; a LOW quick pass *is* the saucer pass (loft math in `ShotMechanics.loft_y`; per-level speeds `loft_vertical_speed_*` on `SkaterController`).

**Skating is momentum-driven.** Thrust accelerates, drag-friction decelerates naturally, Space brakes hard (heavy friction, direction-agnostic). Backward and lateral (crossover) movement are slower than forward. Facing lazily tracks the cursor, and auto-freezes during shot aim/charge/block states and when the cursor swings into the unreachable wedge behind the skater. No frame-perfect inputs — reads and positioning matter more than execution precision.

**Sprint (Shift) is a stamina-gated top-speed burst.** Holding sprint while skating raises the speed cap (and bumps thrust to reach it) but *widens the turn radius* (`sprint_turn_multiplier` scales facing turn rate in `SkaterPoseCoordinator.apply_facing`) — committed straight-line speed traded for agility, so it's a read rather than a hold-always button. It drains a stamina pool; carrying the puck drains it faster. Empty the pool and sprint locks out until it regenerates past half. The gauge is a BOTW-style **stamina ring** nested inside the local player's own on-ice color ring (`SkaterHUDCoordinator`, self-only): hidden while full, amber when low, flashing red during the exhaustion lockout. Stamina is a 0..1 pool computed by `stamina_rules.gd` (pure/deterministic so it survives reconcile replay), replicated on `SkaterNetworkState` and snapped from the host at replay start like velocity. Tunables (`sprint_*`, `stamina_regen_per_sec`) live on `SkaterController`. Stamina is **Weight-flavored metabolism** (attributes v4 — the fork rides the frame dial, no other lever touches it): a lean player has a shallower pool (drains faster) but recovers fast, a heavy player a deep pool (drains slow) but slow recovery — lean = short repeatable bursts, heavy = one long drive then a slow refill. The sprint *ceiling* is speed-normalized and grounded to the 20–25 mph NHL burst band (`sprint_ceiling_mult`); body-only builds sit in a tight middle band and the skate-profile gear slot re-widens it (~20.5–24 mph) — see **Player Attributes → Sprint & carry**.

**Physicality is emergent, not scripted.** Body checks trigger from closing-velocity impulse, not a hit button. Ctrl crouches to shot-block (wider hitbox, reflects shots). Poke-checks are stick-on-stick momentum contests — the blades collide and the puck goes where the blended momentum sends it. **Contested pickups** — two blades reaching the same loose puck (a faceoff draw or a board scramble) — are the same kind of contest: nobody is ever awarded possession, the puck squirts free *biased toward the stronger blade's momentum* (a true 50/50 pops out sideways, the "pinched seed"). One resolution, `PuckCollisionRules.contested_pickup_velocity`, shared by the host's present-time pickup tick and the networked lag-comp claim path, so scrambles feel identical however the contestants are hosted. Blade speed already reflects Hands, so the draw rewards the better dangler emergently — no attribute term.

**A hard check staggers its victim.** Beyond the knockback impulse, absorbing a check inflicts a temporary thrust penalty plus a stamina bite, both scaled by how hard it landed — the m/s transfer impulse, which already folds in attacker Size/Physical and the closing Speed, and victim mass. The math is pure (`Scripts/domain/rules/body_check_rules.gd`): hit strength normalizes to a 0..1 intensity between `stagger_min_impulse` and `stagger_ref_impulse`, and a single value, `stagger_timer` (seconds remaining), encodes **both** the penalty depth and the recovery window — a harder hit sets a longer timer, and the per-tick thrust penalty is proportional to the time left, so it eases back to full thrust on its own. The stamina bite charges only the stagger a hit adds *beyond* the residual (`incremental_stamina_drain`), so a clean hit bites full but grinding someone on the boards bleeds at ~the decay rate instead of emptying the pool tick-by-tick. The debuff is host-authoritative (victim-only `Skater.body_check_received` signal — distinct from the both-roles `body_check_impulse_applied`, so a delivered hit's restitution bounce never self-staggers the attacker) and replicated as `stagger_timer`, snapped and re-derived through reconcile exactly like stamina. Tunables (`stagger_*`) live on `SkaterController`; flat for all players in v1 (the hit strength already reflects the combatants' attributes). **Check feedback scales with hit strength too:** the burst (particle count + velocity) and impact sound (volume + pitch) read the same intensity in `SkaterVFX`, which owns one throttled code path for both — a short cosmetic de-dup window coalesces the per-tick re-fires of `body_checked_player` during sustained contact so one hit reads as one impact. (Genuine head-on collisions still emit from both bodies by design — two impact points.)

**Goalies are AI-only, never player-controlled.** Tuned for *beatable realism* — they should look and move like a real goalie while staying deliberately scorable (the realism additions only ever open scoring windows, never buff a set goalie into a brick wall). Reactive with a small reaction delay (the window for close-range top-corner goals) that a **pre-armed read** shortens when the goalie has been fixated on a visible windup (quiet-eye anticipation — a quick-release snap *from range* never earns the windup prime), and that an opposing carrier already **in the slot arms by proximity** (`prime_slot_distance`, set-and-sighted — a coiled goalie is never a frozen statue on a quick in-tight release; the prime only makes the limbs *start* moving, the reach-speed cap still bounds coverage so you beat him by picking a corner out of reach); positional depth chart on the challenge-angle arc, with a **speed-matched rush backflow** (a closing carrier retreats the goalie along the taught curve at the attacker's pace — decelerating strands him out at challenge depth); butterfly with a commit timer to prevent toggling and a **grounded ~0.2 s drop** (measured pro drop speed, so clean low shots in tight beat a purely reactive drop — sealing early via the proactive triggers is the counter); **squares to the puck, not the shooter's body** (dangle jitter is absorbed by distance-scaled tracking lag — the quiet-eye smoothing — rather than by aiming at the chest). The read degrades exactly when a real goalie's would: **screened** (a body in the puck→goalie sightline delays pickup, and a *fully* screened release flips save selection to a blocking butterfly — drop on the read, eat the top-corner exposure) and **caught moving / unset** (mid-push, sliding, or standing up reads the shot late). Lateral pushes **accelerate onto the edge** (`lateral_accel`) rather than snapping to speed, so quick cross-ice plays beat the goalie across; when the cross-crease race is *already lost* the goalie goes **pads-first** (drop-and-slide toward the crossing) instead of arriving late upright. Two anticipatory reads guard the back door: a live **weak-side one-timer man caps the challenge depth** (`backdoor_depth_cap` — a pass-flight vs. re-square race, so respecting the back door opens the carrier's direct-shot angle instead), and a lateral drive that **wins the race to the post** (`is_beaten_wide` — keyed on the *puck*, not the body: a forehand-drag drive with the puck trailing commits nothing until the puck crosses the goalie's sealing reach, the point of no return — and it must be a *sustained* drive — carrier-driven lateral commits hold for a quiet-eye confirmation beat, `lateral_commit_confirm_s`, so a deke's transient spike un-commits when pulled back; pass-driven seals stay instant since a puck in flight can't cut back) drops the goalie into the butterfly-slide post seal rather than an unwinnable standing chase — baiting that committed drop with a fake held past the confirmation is the counter. Post play splits at the goal line: **RVH** seals at/below it (wraps, walkouts, dead angles), **VH** — post pad vertical, body tall — takes the in-front sharp-angle shot threat, closing RVH's short-side-high hole. While down, the goalie **knee-shuffles** (slow sealed micro-scoots toward the arc target) between committed slides — the real three-tier down movement — and the **head tracks the raw puck** in every state (eyes-lead; the body plays the smoothed threat). A committed **stick lunge is a gamble** (fully-unset read while extended). Loose pucks in the crease follow the real cover-vs-clear hierarchy: the corner sweep is **lane-aware** (exit corner picked by opponent reach-vs-flight — `sweep_lane_blocked`; a covered lane flips corners), and when **every lane is covered with an opponent on the puck, the goalie smothers it** (`COVERING` — a glove-race cover that a well-timed whack still beats), and a puck that comes to **rest on the goalie's body** (a deadened save settling on the pad tops — the only body that can support a puck off the ice) triggers the same smother, since no blade can legally reach it there. The cover resolves by ruleset: `NHL` whistles the play dead and faces off in the defensive zone; `ARCADE`/`OFF` run a flow-preserving **hold-and-release** (~0.85 s of dead puck that kills the scramble and lets the defense reset, then the goalie plays it out himself through the same lane-aware sweep — no stoppage, the same philosophy as the offside ghost), spaced by a cover cooldown. Bots treat the covered puck as dead (the loose-puck chase election returns nobody while it's locked), so they reset to their slots instead of crowding the smother. The goalie also **plays rims behind the net** — tier-1 conservative only ("stop it, leave it, get back"): a paddle-down trap at the boards directly behind the cage, gated by an ultra-conservative go/no-go race (full-sprint forechecker assumption, whole-trip clock, fat margin, net-front lurker veto) and re-checked every tick with a stricter abort margin so he visibly bails early rather than ever getting caught out; he never carries or passes (the misplay-prone tiers of real puck handling are deliberately absent), the trip routes around the post via a waypoint — skated with a real stride (a procedural gait borrowed from the skater's stroke warp, distance-driven so it freezes when he stops; PLAYING_PUCK only, the crease glide is correct goaltending) — and only the HARD tier plays the puck at all (`GoalieSkillProfile.puck_play_go_margin_s` is INF below it). Saves follow real rebound doctrine: the chest **absorbs dead**, the glove **catches and holds** (squeeze-and-look — a catch under pressure freezes the play through the same rails as the smother, NHL whistle / ARCADE hold; an unpressured catch look-and-drops after a beat and plays on, the real delay-of-game incentive), controlled pad/blocker saves are **steered cornerward at pace** (modern active rebounds — `GoalieSaveRules`), hard shots beat the pad and kick a live rebound; angled pads (pose toe-out + pad material, not a physics override) keep deflections out of the slot. Pure read/positioning/rebound math lives in `Scripts/domain/rules/goalie_behavior_rules.gd`; tuning is `@export`s on `Scripts/controllers/goalie_controller.gd`.

**Game format:** 3v3 or 5v5 (the lobby's Mode row; `team_size` latches at puck drop exactly like the ruleset, and OT keeps the match's size), three periods plus optional OT, period length tunable. In 5v5 the lobby slot IS the position (LD/LW/C/RW/RD — `team_slot` 3/1/0/2/4): the AI's role layer branches at one seam (`TeamBrain` → `AIRoleSlots5`, a group-scoped election where D and F compete only for their group's jobs, cross-filling when a group runs short), the D-zone runs the researched hybrid zone (`zone_coverage.gd` + `zone_defense.gd`), points/line-holds/valve live in `defenseman.gd`, and the carrier's turnover price gains the 5v5-gated **transition-exposure** counter-rush term (`AIActionScoring.counter_rush_cost`). The 3v3 role path is untouched by construction. Faceoffs have a short "2 → 1 → DROP" prep; the drop is a **live** puck (no possession assignment), so winning the draw is a real contested pickup — see *Physicality* above — decided by which center's blade wins the momentum contest at the dot. **Offsides** ghost the offending player (can't interact with the puck) until they tag back to the blue line in `ARCADE`; `NHL` instead runs true delayed offside (tracked but not ghosted — a whistle only fires if the offending team touches the puck, or makes physical contact with a defender, before tagging up — the latter stands in for the real rule's "forces the puck carrier back" / "about to make contact" linesman judgment calls with one deterministic trigger: any contact between the two teams while the delay is active). Both rulesets void it two ways, matching the real rule: the puck fully clearing the attacking zone, or the **defending team establishing possession** (PossessionTracker's ESTABLISHED standard — held it or made a deliberate play, the same "control" bar stat attribution already uses, not a bare touch) while the puck is still in the zone — either way the previously-offside player becomes fully onside without needing to physically tag up. `ARCADE`'s instant ghost is meant to emulate this same underlying rule, it just never produces a stoppage, so it voids on the same conditions NHL does. **Icing** (NHL ruleset only) is a whistle-and-faceoff rule — hybrid-icing race, then a faceoff in the offending team's end; it does **not** ghost the team (the default `ARCADE`/`OFF` sets don't detect icing at all). **Goalie covers** split the same way: `NHL` whistles a defensive-zone faceoff when the goalie smothers a loose puck; `ARCADE`/`OFF` keep play rolling via the goalie's short hold-and-release (see the goalie section). **Crease camping** (dwell-timer ghost, `CREASE_DWELL_DURATION`) is an `ARCADE`-only anti-cheese mechanic, not a real NHL rule — real goaltender interference is contact-based and screening without contact is legal, so it's dropped from `NHL` until a real contact-based interference system exists. Goals trigger a short pause + celebration window. Between periods a fixed 20 s intermission shows the score band + countdown, with the ended period's goals looping behind it when there are any (unanimous Space vote skips the break, like the goal replay), and the post-game screen reveals **Three Stars** over the full-match highlight loop. The default ruleset is `ARCADE` — offsides on, icing off by default — because strict sim rules get in the way of the fast, casual flow.

**Smart ping (G, rebindable) — one context-sensitive team message.** One key, no menu: what the cursor is on, crossed with the possession state, picks the call-out (`PingRules.resolve`, a pure GUT-tested decision table): self → *"Pass to me!"* / *"I'm open!"*; the carrying teammate → *"Shoot!"*; an off-puck teammate → *"Get the puck!"* / *"Get open!"* / *"Pick him up!"* by who possesses; the opposing carrier → *"Get him!"*; an off-puck opponent → *"Cover him!"*; the loose puck → *"Get the puck!"*; bare ice → *"Over there!"*. Display is **team-only** (a ping never telegraphs to opponents): a chat bubble above the pinger's head (`SkaterHUDCoordinator.show_ping_bubble`), except the location ping which drops a pulsing ring + floating text at the spot (`PingMarker`). **Bots obey**: the host routes each ping into the pinger's `TeamBrain` as a bounded directive (`AIPingDirectives`, ~3–6 s expiry, one live order per pinger) that rides the existing role architecture rather than bypassing it — pass/shoot pings are EV **biases** in the carrier's compete (×3, so any remotely reasonable read wins but a hopeless order is still vetoed — never a forced giveaway), cover/pressure/get-open pings force-slot the obeying bot (MARK with a pinned man / PRESSURE / FINISHER), retrieval pings override the chase election, and location pings commandeer steering only. A directed ping at a bot orders *that* bot; at a human it's just the bubble. Cooldown ~1.5 s/player, enforced client- and host-side. Wire: one vote-shaped reliable RPC pair (`request_smart_ping` / `notify_smart_ping`), self-fired locally so offline free play works identically.

**Tone is casual and responsive with a competitive ceiling.** The physics are responsive and forgiving on the surface, but blade placement, shot timing, charge management, and positioning meaningfully separate skilled play. Pick-up-and-play, hard to master.

**Where the numbers live** (don't bake these into prose — read them when you need them): movement, shot, and body-check-stagger tuning (`sprint_*`, `stagger_*`) in `Scripts/controllers/skater_controller.gd`; shot math in `Scripts/domain/rules/shot_mechanics.gd`; stagger math in `Scripts/domain/rules/body_check_rules.gd`; period/faceoff/offsides/icing constants and presets in `Scripts/domain/config/game_rules.gd`; goalie tuning in `Scripts/controllers/goalie_controller.gd`; **per-player attribute tables** (attributes v4: Height + Weight body dials + gear slots → gameplay + visual effects) in `Scripts/domain/state/player_attributes.gd`; 5v5 zone-coverage geometry in `Scripts/domain/ai/zone_coverage.gd`, the 5v5 election targets/bias in `Scripts/domain/ai/role_slots_5v5.gd`, and the transition-exposure appetite scalars on `Scripts/domain/ai/role_behaviors/carrier.gd`.

## Player Attributes

A build is **BODY + GEAR** (attributes v4 — design of record in `docs/attributes-v4-plan.md`; the tier system is gone): two permanent continuous **body dials** — **Height** (inches, every inch 5'7"–6'8", tables authored at 5 anchors and interpolated; the range was extended 2026-07 by MOVING the end anchors out rather than adding rows, each end row rebalanced so the outer segment's per-inch slope just continues one more inch — so every previously-playable height kept its values and the two new ones genuinely extend each curve) and **Weight** (lbs, bounded per height by a **BMI band 23.0–29.0** floored at an absolute **162 lb** playable mass (two independent floors: the ratio governs 5'11"+, the absolute governs 5'7"–5'10" where a ratio stops meaning anything — 162 is the lightest player in the NHL), so implausible bodies are unrepresentable by construction; neutral 26.5, and the band is asymmetric about it so `frame_t` is piecewise — min/neutral/max pin to 0/0.5/1 at every height. Recalibrated 2026-07 against listed NHL cards: BMI is the right normalizer — the sample's weight-vs-height allometric exponent is 2.01 — but the old flat 24.0 lean floor was set by short players, whose lower tail is truncated by an *absolute* mass bound rather than a ratio, and it wrongly forbade real tall-lean bodies like 6'4"/195. Both edges are set at the distribution's shape, not its most extreme member — each excludes ~2 tail bodies, and neither is stretched to catch its outlier) — plus four lateral **gear slots** (skate profile, blade curve, stick flex, stick length; 0/1/2, 1 = balanced). **There is no power economy**: every axis is lateral, so there is no legal shape, no `is_legal_build` — validation is pure coercion (`coerce_height` / `coerce_weight` / gear clamps; a forged build lands on the nearest legal body). Neutral reference is **6'1" / 201 lbs / all-balanced** (the real NHL-average frame), where every gameplay multiplier is 1.0 (= the shipped `@export` defaults). **Gear slots — three of four live**: **STICK LENGTH** (short/standard/long — a ±4% lean on the height's cut, feeding reach, poke/claim range, the blade-cap lever, the wrister full-stroke rescale, and the stick mesh); **BLADE CURVE** (closed/balanced/open — the blade **FACE ANGLE** (23°/31°/45°) caps the shot's launch angle in `ShotMechanics.loft_y`, so at pace every curve reaches the same per-level apex — the crossbar ceiling holds for all blades — while the *soft* steep release that roofs in tight is face-gated: min bar-height roofing distance emerges at ~2.2 m open / ~3.7 m balanced / ~5.2 m closed, and the standstill saucer flip flattens on a closed blade; trajectory is a pure function of power + level + face, never position; open's 45° = the pre-curve universal cap, bit-identical; curve also leans the wrister runway and the backhand coefficient toward-but-never-past parity); **STICK FLEX** (whippy/medium/stiff — leans the shot ceiling WITH the slapper wind-up and wrister runway, a true lateral seesaw, deliberately unlike the height coupling where a harder shot also threatens sooner). The stacked quick-release loadout (whippy+open) bottoms at 81% of the neutral runway — the runway floor that keeps a max-power release readable to the goalie (NOTE: the "runway" IS the wrister travel gate, currently DORMANT — see the Wrister bullet; `apply_attributes` still rescales it, but nothing reads it while the blade is frozen); **SKATE PROFILE** (agility/balanced/power — the blade grind: power = +top speed/glide, −agility incl. `lateral_grip`; agility = +first step/cornering, −top speed; this is what re-widens the sprint band the body plane compressed, ~20.5–24 mph across profiles; stacked body×gear agility corners pinned by test at ~0.84–1.15). **All four slots are live.** Bots price their own gear: `AISkaterCaps.loft_tan_max` feeds the HIGH-hole solver's face floor (a closed-blade bot knows its real minimum roofing distance), `AISkaterCaps.lateral_grip` feeds the planning models everywhere a direction change is priced (the ETA cross-momentum shed, each defender's `reach_clearance` shed, the deke's lateral bite/unwind budgets — calibration-tested against a gripped real-physics sim), and blade caps/reach/backhand ride the caps as before; the one residual drift (defensive reads of opponents assume an open face — conservative) is noted in the plan doc. The picker (`attribute_picker_panel.gd`, built in code) is two sliders — height, and weight bounded to the height's band (moving height preserves the frame fraction, so a lean build stays lean as it grows) — plus the stick-length three-way row. Bots have curated cards in `data/bot_identities.json` (`{height, weight, gear…}` — hockey-card readable). Online matches lock the build at join time (replicated as **6 ints** — height, weight, profile, curve, flex, length — through `request_join` / `spawn_remote_skater`, `PROTOCOL_VERSION` v37); free-play picks re-apply immediately without a respawn.

The routing (the constitution: a lever may scale **outputs** or **geometry**, never **fidelity** — see the plan doc §1):
- **Height** → speed↔agility baseline fork (`max_speed` hump peaks at 6'1"; agility small-favored), **shot-power baseline** (big-favored, ~89.5 mph neutral slapper → ~98.7 mph at 6'8" body-only; gear re-widens the top end later), reach / mesh scale / arm-ROM / stick length (mesh-native 5'10" is the reach-1.0 anchor), hitbox radius. *(+ visual height, torso/head bulk)*
- **Weight** → **mass** (`mass_mult = lbs/201`, LINEAR and wide 0.79–1.28 — with no Checking stat, mass IS the physical system: delivery and brace are body-emergent through the collision resolver's reduced-mass math, `check_delivery_mult`/`brace_mult` are flat 1.0), **accel↔momentum fork** (lean = first-step burst; momentum is mass-emergent), an **agility bite** (F = mv²/r, delivered mechanically by `lateral_grip` — agility scales the perpendicular-to-motion thrust authority in `SkaterMovementRules`, so the turn *radius* itself widens/tightens per build; heavy turns wide and stops long, **glide is exempt** so the tank still coasts, and top speed stays weight-free), **hitbox width** (tracks the frame bulk), and **stamina metabolism** (lean = shallow pool/fast regen, heavy = deep pool/slow refill — moved off height). *(+ uniform limb/shoulder frame bulk — silhouette = body: height scales the skeleton, weight scales the girth)*
- **Hands** → **nothing, by constitution** ("your hands are you"): `hands_blade_mult()`/`hands_backhand_mult()` are 1.0 for every build. Hands differentiation is delivered as lever *geometry*, never a multiplier: the blade caps derive from the build's actual sweep lever (stick + arm ROM, normalized to the 6'1"/standard neutral) — **tip speed ∝ lever** (same angular gesture, faster blade in m/s; traverse time across your own reach stays ~flat, pinned ≤8% by `test_blade_lever_calibration`) and the **inertia cap ∝ 1/lever^k** (`blade_inertia_exponent`, default 1.2) — the long lever sweeps, the short lever cuts back. The second-order blade servo ships **ON** (`max_blade_accel = 250`, `blade_inertia_exponent = 1.6` — playtest-calibrated across the min/neutral/max builds; 0 disables it, reverting to the pre-v4 first-order servo bit-exact).

**Sprint & carry:** the sprint **ceiling** is still speed-normalized over the full v3 span (`sprint_ceiling_mult`), so body-only builds sit in a tight ~22 mph middle band until the skate-profile gear slot re-widens it; the carry penalty is **Speed-eased only** (the v3 Hands term is folded into `CARRY_BASE` so neutral is unchanged at ~0.958); the real cost of carrying at speed remains the **1.6× sprint stamina drain** (`sprint_carry_penalty_bypass` unchanged).

All tuning lives as private tables on `PlayerAttributes`, read via named accessors (`attrs.speed_mult()`, `accel_mult()`, `mass_mult()`, `sprint_ceiling_mult()`, …) — **never index a `_*` table outside that file**. Height tables are 5-vecs at the anchor heights; frame tables are 5-vecs lean→heavy indexed by `frame_t()` (position in the integer pounds band, so band edges and the 73"/201 neutral are exact). Derived/coupled levers are computed from their partner so they can't drift (edge glide = `2 − agility`, slapper wind-up = `2 − shot power`). To add a new "X scales Y" rule, see the doc-block at the top of `player_attributes.gd`.

Application path: `SkaterController.apply_attributes(attrs)` reads the accessors and writes scaled values to controller `@export`s, `Skater.weight`, etc.; `SkaterAppearanceCoordinator.apply(attrs)` does the visual mesh scaling. Both are idempotent — they capture baseline values on first call and recompute from baselines every subsequent call, so repeated applies (free-play picker changes) never compound. **Prefs migration** (`player_prefs.gd`, gated by `attr_scale_version`, now v5): a v4 tier save maps deterministically via `PlayerAttributes.migrate_tiers` (Checking→frame weight, strong Skating→profile lean, strong Skill→open curve or short stick by height, strong Checking→long stick); older six-attribute saves chain through `migrate_legacy` → `migrate_tiers`. Bot rosters and stored presets migrate through the same `from_dict` seam.

## Layer Architecture

The codebase is split into three layers; dependencies always flow downward:

- **Domain** (`Scripts/domain/`) — pure GDScript, no engine APIs. Rule classes (static methods), the game state machine (RefCounted), enums, and game-rule constants. Fully unit-testable without Godot.
- **Application** — `GameManager` (autoload orchestrator), controllers, `ActorSpawner`, and six RefCounted collaborators. Use the domain to make decisions; reach into infrastructure to execute them.
- **Infrastructure** — actor nodes (Skater, Puck, Goalie), `NetworkManager`, UI. The Godot-side glue.

Lower layers never reach up: actors take their collaborators via `setup()` (e.g. `Puck.set_team_resolver(Callable)`); controllers take a `game_state: Node` exposing `is_host()` / `is_movement_locked()`). Upward communication is by signals that the orchestrator listens to.

See `ARCHITECTURE.md` → **Confusing Boundaries** for class-responsibility detail (`GameStateMachine` vs `PhaseCoordinator` vs `GameManager`, `constants.gd` vs `game_rules.gd`, `SkaterController`'s five `RefCounted` collaborators, etc.).

## Code Conventions

**Strong typing everywhere.** Typed arrays (`Array[BufferedPuckState]`), typed function signatures, typed variables. Never leave a type annotation off when it can be provided. Prefer `var state: PuckNetworkState` over `var state`.

**Cast or annotate when chaining through superclass APIs.** GDScript's type inference can't see through methods that return a base class — e.g. `Engine.get_main_loop()` returns `MainLoop`, not `SceneTree`, so `var scene := Engine.get_main_loop().current_scene` fails to infer. Same pattern for `find_child()` (returns `Node`, not the subclass), `get_node()`, `instance_from_id()`, etc. Add an explicit type (`var scene: Node = ...`) or a cast (`as SceneTree`, `as Node3D`) so the analyzer can resolve member access on the next line. The fix is mechanical; don't ship inferred-from-superclass typing.

**Godot naming conventions.** `snake_case` for variables and functions, `PascalCase` for class names, `SCREAMING_SNAKE_CASE` for constants.

**Separation of concerns.** Physics bodies (`Puck`, `Skater`) expose a clean API. Controllers drive them. `GameManager` owns spawning and world state. `NetworkManager` owns RPCs. Don't reach across these boundaries casually.

**Network API uses typed objects, not raw arrays.** Functions accept `SkaterNetworkState` / `PuckNetworkState` directly. Serialization happens only at the RPC boundary.

**Get it working, then tune numbers.** Use `@export` on tunable parameters so values can be adjusted in the editor. Don't prematurely optimize or bikeshed on constants before the mechanic runs. **Live editor tuning is not a workflow here** — the developer doesn't tweak exports while the game runs, so hot-path code may cache config objects built from exports (rebuilt on `apply_attributes`) without preserving per-tick rebuild semantics. Don't undo config caching to restore live-tuning.

**Grounded models over magic-number curves — in evaluation code especially.** When code *evaluates* a situation — the bot AI's utility scoring, the goalie's read, any "how dangerous / open / safe is this?" number — build the result from a model of quantities the actor can physically "see," not a curve shaped to feel right. Every multiplier should read as real data: the open-net angle a shooter can hit, a defender's reach vs. the puck's flight time, the goal mouth's projected width — not `1 − x/K`. The payoff is leverage — a grounded model generalizes to cases you never tuned and stays honest when an upstream number moves — so it's worth more up front than a curve. When a behavior is wrong, fix the *model* (give it the perception it's missing); don't bolt on a corrective hack or a hard positional gate, which only compensates for a model that isn't seeing something and then rots. A magic curve in an evaluator is a model you haven't built yet. This is **not** a ban on hand-set numbers: *feel / tactical* tunables — `stagger_*`, staging offsets, loft heights, difficulty knobs, how the game should *play* — are legitimately chosen by hand. The line is evaluation vs. feel; when you must add a constant to an evaluator, make it a physical measurement (a reaction delay, a reach, a body width), not a shape parameter. See `ARCHITECTURE.md` → **Bot AI** for how the scoring models embody this.

**Hot-path discipline — the 120 Hz tick multiplies every cost.** Anything reached from `_physics_process` or a per-tick controller `update()` runs 120×/second × actor count (6 skaters + 2 goalies + puck), and reconcile replay re-runs the per-tick body once *per replayed input* — so a hot-path cost is amplified again exactly when the network is bad. The host's per-tick budget is shared: when it overruns, physics dilates against the wall clock, and because the broadcast cadence is counted in physics ticks (`network_manager.gd` `_state_tick_divisor`), *every client's* update rate sags with it. A single host-side hot-path regression degrades the whole lobby. Two failure modes, in order of impact: **(1) Allocation churn** — short-lived heap objects per tick: `.new()`, Dictionary/Array literals, `.filter()`/`.map()`/lambdas, `x in [literal]`, returning a fresh `Dictionary`/`Array`, per-call `String` formatting — pressures GDScript's allocator/refcount on the main thread; this is the dominant cost (audit P1–P5). Value types (`Vector3`, `Basis`, `Transform3D`) do **not** heap-allocate, so the math is cheap — the enemy is the heap object, not the arithmetic. **(2) Unnecessary cosmetic work** — visual-only updates (mesh/arm IK, `look_at`, decals) that don't feed gameplay belong in `_process` (render rate), not `_physics_process`, and should skip when idle (dirty-flag) or off-screen (visibility cull); gameplay reads the `blade`/`Marker3D` anchors, not the cosmetic mesh, so cosmetic IK at tick rate is pure waste (audit P2, P8). **Keep the layer boundary AND the performance — they don't conflict:** a Callable/collaborator boundary is an interface, not a license to allocate per call. *Memoize at the seam* — cache the result and invalidate on change (`PlayerRegistry` caches `Array[Skater]`; `puck_controller` caches `team_id_by_skater`). *Build once, fill scratch* — configs that only change on `apply_attributes` are built there and reused; solvers fill a caller-owned result instead of returning a fresh `Dictionary` (`GoalieBodyConfigBuilder`'s shared scratch config is the model). Before adding per-tick code, ask: does it run at 120 Hz × actors? does it allocate? is it cosmetic (→ `_process` + dirty/visibility guard)? Spot a hot-path allocation while working nearby — flag it per the bug-flagging rule; the standing backlog lives in **GitHub issues**. This is not in tension with "get it working, then tune numbers" above — that's about *constants/feel*; this is about *structure*, and structure is cheaper to get right up front than to retrofit.

**Don't shy away from complexity when it improves feel.** This project already has full client-side prediction with input replay, buffered interpolation, and puck trajectory prediction with reconciliation. If adding a complex system will make the game feel meaningfully better to play, it's worth doing — think it through carefully first, then implement it properly.

**All popups and modal dialogs must be closeable via `ui_cancel` (Escape).** Add the popup to the existing `_unhandled_input` block in the relevant UI script — check `popup.visible`, hide it, and call `get_viewport().set_input_as_handled()`.

## Launch Modes

All start paths go through `Boot.tscn` (title card): `boot.gd` threaded-loads `Hockey.tscn`, then drops the player into free play via `NetworkManager.start_free_play()` (a boot where the player has never touched the tutorial course routes into its first part via `start_tutorial()` instead — finishing or exiting any part counts as touched, so the course is seen once but never nagged; it's catalogued in `TutorialRegistry`, lives on in the **Tutorial** menu (drills are a separate **Drills** menu, catalogued in `DrillRegistry`), and `PlayerPrefs.TUTORIAL_COURSE_VERSION` wipes saved completion when the course is restructured so everyone passes the gate again). From there the HUD's `SideMenu` drives session changes through one **Play** popup — Start Game runs `start_offline()` and enters the unified lobby (instant, no Steam needed), and the open-games browser joins via `start_client_lobby(lobby_id)`. `NetworkManager._ready()` does nothing. **Hosting is a lobby-phase state, not a menu path**: the lobby's host-only visibility selector (Offline / Friends / Public) attaches the Steam transport via `NetworkManager.attach_online(public)` — safe because it only runs with zero peers, and the offline session already runs the full host simulation (the `is_offline_mode` gates only stop broadcast/ping/upload) — and `detach_online()` returns to Offline (locked out while human peers are connected; the host kicks via the slot grid first). Friends ↔ Public is a live `SteamManager.set_lobby_visibility` (`Steam.setLobbyType`) flip. A match's online-ness is fixed at puck drop. **Backend career uploads are NOT gated on it** — every real match (offline vs bots included) posts a `career_stats` row, gated only on `_achievements_active()` (not free play / tutorial / drills), `PlayerPrefs.share_gameplay_stats`, and a signed-in Steam identity; the session type rides along as data (`is_online`, plus `human_players` — the peak human headcount, a count rather than a "ranked" flag since Mitts has no ranked mode) so a human-only filter stays possible later without having discarded offline play. Network-quality rows (`network_sessions`) remain online-only — an offline match has no link to measure. Online transport is **Steam P2P via `SteamMultiplayerPeer`** (GodotSteam GDExtension), a drop-in `MultiplayerPeer`, so all RPCs/prediction/reconcile/lag-comp are transport-agnostic and unchanged. Unlike ENet's instant `create_server`/`create_client`, Steam lobby create/join are **async**: `attach_online()` waits for `SteamManager.lobby_created` then emits `host_lobby_ready` (the visibility selector shows a busy state until it lands); `start_client_lobby()` waits for `lobby_joined`, reads the lobby owner's Steam ID, then the normal `connected_to_server` handshake runs unchanged. `Hockey.tscn`'s root node runs `game_scene.gd`, whose `_ready()` calls `NetworkManager.on_game_scene_ready()`, which emits `host_ready` on hosts; `GameManager` listens and calls `on_host_started`. Client world spawn is triggered by the `client_connected` signal from `_on_connected_to_server()`.

NetworkManager → GameManager communication is signal-based: every RPC / ENet callback emits a typed signal, and GameManager wires all connections once in `_ready()` via `_wire_network_signals()`. The only downward data flow is `NetworkManager.set_world_state_provider(Callable)`.

## Distribution

Playtester builds ship via GitHub Releases (`latest` tag). `deploy.yml` computes `VERSION=0.1.<git rev-list --count HEAD>`, rewrites the placeholder `"dev"` in `Scripts/game/build_info.gd` to that string before export, and publishes with the version as the release name (plus an immutable `v0.1.N` prerelease per build for rollback). Steam (SteamPipe) now handles distribution and auto-updates for the closed beta (`steam/` holds the upload scripts); the old GitHub-release `UpdateChecker` startup notifier has been removed since Steam owns updates. No in-game patching/downloader.

**Supabase backend:** `Scripts/game/supabase_config.gd` holds the project URL and publishable (anon) key — safe to commit, RLS restricts it to INSERT/SELECT/UPDATE. `CareerStatsReporter` (`Scripts/game/career_stats_reporter.gd`) POSTs one row to `career_stats` at game-over and GETs from the `career_totals` view for the career screen. `BugReporter` (`Scripts/game/bug_reporter.gd`) POSTs to `bug_reports` with a telemetry snapshot. `NetworkSessionReporter` (`Scripts/game/network_session_reporter.gd`) POSTs one connection-quality row per online game to `network_sessions` at game-over — the playtesting telemetry pipeline (see `ARCHITECTURE.md` → **Playtesting telemetry**; schema + analysis view in `supabase/migrations/*_network_sessions.sql`). All use fire-and-forget `HTTPRequest` nodes added to the scene tree root and fail silently. The secret key must never be committed — use only the publishable key in `SupabaseConfig`. **Table/view/RPC schemas are version-controlled as migrations in `supabase/migrations/`**, applied to the hosted project by `.github/workflows/supabase.yml` on merge to `main` — a schema change ships with the code that needs it rather than being pasted into the SQL editor. Migrations are idempotent DDL and CI pins that (it replays them onto a populated DB); `supabase/README.md` is the full workflow, including the one repo secret the pipeline stays inert without. All backend rows key on `steam_id` — there is no per-player `uuid` (`game_id` is still a UUID, minted by `PlayerPrefs.generate_uuid`).
