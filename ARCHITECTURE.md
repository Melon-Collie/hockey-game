# Architecture

Technical decisions and reference tables for Mitts. Layer model, code conventions, and development workflow are in `CLAUDE.md`.

---

## Design Philosophy

Depth over breadth — few inputs with rich emergent behavior rather than many explicit mechanics.

The Rocket League freeplay ceiling is a guiding star: the stickhandling-to-shot pipeline should reward practice and feel satisfying to master.

**Key inspirations:** Omega Strikers / Rocket League (structure), Breakpoint (twin-stick melee blade feel), Mario Superstar Baseball (stylized characters, exaggerated tuning, pre-match draft). Slapshot: Rebound is a cautionary reference — pure physics shooting feels unintuitive; the blade proximity pickup system is explicitly designed to solve that accessibility gap.

## Reference

### Network Rates

| Channel | Rate | Transport |
|---------|------|-----------|
| Input (client → host) | 120 Hz | Unreliable, last 12 frames per packet (24 above 10% loss) |
| World state (host → clients) | 60 Hz | Unreliable, ~384 bytes at 6 players + 2 goalies (single flat PackedByteArray + 1-byte carrier-event block when idle, +13 B per in-flight carrier event; well under 1392-byte ENet MTU) |
| Events (spawn, goal, goalie transitions) | On event | Reliable |
| Carrier events (pickup grant, carrier change, steal, drop) | On event | Reliable backstop **+** redundant copy in every world-state packet for ~1 s (`SnapshotEventLog` trailing block; seq-deduped) |
| Stats sync | On change | Reliable |

Interpolation delay: 75ms baseline, adapts per-packet via `lerp(0.15)`, capped at +10ms / −1.5ms per packet (per-PACKET steps, so the effective per-second rates halve with the 60 Hz broadcast — see `adapt_interpolation_delay`). **One shared delay** drives every remote interpolator (remote skaters, loose puck, goalie): `NetworkManager._interp_delay`, advanced once per received world-state packet in `receive_world_state` and read via `get_interpolation_delay()`. Per-actor independently-adapting delays used to drift apart, skewing relative timing (puck-vs-stick on a pass, save-vs-puck); the single value renders them all at the same instant. `get_target_interpolation_delay()` is cached per physics frame (it sorts the jitter buffer).

Wire format: Skater 37B · Puck 13B · Goalie 35B (12 B root + 23 B pose). Quantized; ~50% reduction vs unquantized. Puck Y is s16 (not s8) so elevated/saucer shots above the s8 ±1.27 m range don't clip flat on the wire.

**Input timestamp lead:** Client inputs are stamped with `NetworkManager.estimated_input_stamp_time()` = `estimated_host_time() + INPUT_LEAD_SEC` (~25ms). `estimated_host_time()` already encodes the NTP-measured RTT/2, so inputs arrive at the host at approximately their timestamp. The 25ms lead = 8.3ms worst-case batch-send jitter (input batches go out once per 120 Hz tick) + 16.7ms two-tick buffer, ensuring the host input queue never starves between batches. (History: the lead was designed as 25ms at the 240 Hz tick, silently grew to 33.3ms when the tick halved — `BATCH_INTERVAL` was hardcoded `1/60` — and returned to a true 25ms when input batching moved to 120 Hz and `BATCH_INTERVAL` was derived from `Constants.INPUT_RATE`.) The host gates consumption in `RemoteController._drive_from_input`: inputs are held until `host_timestamp <= estimated_host_time()`. The F3 overlay's host-only "Client input queue" section reports `Input lead` and `Starvations` — healthy values are lead ≈ 0–8ms, starvations = 0.

### F3 Network Debug Overlay

`Scripts/ui/network_debug_overlay.gd` — toggled with **F3**. Reads `NetworkTelemetry.instance` + `NetworkManager` every frame and renders a color-coded health readout. It's a diagnostic for "is this lag expected or is something actually broken?", not a raw number dump.

**Reading it:**
- **Header verdict** — `● OK / ● WATCH / ● PROBLEM` rolls up the worst single metric on screen. Green header = nothing needs attention.
- **Per-line dots** — green / yellow / red, thresholded against the documented healthy ranges. Each line also carries a plain-English label and its target range inline, so no separate legend is needed.
- **Info lines** (grey `·`) — context with no health judgment (clock offset, bandwidth, puck mode, buffer depths).
- **Latency budget** (client-only, clock-synced) — end-to-end latency decomposed into named terms so netcode changes are judged by numbers, not feel: `You → host sim` (`INPUT_LEAD_SEC`, by design), `Host → your screen` (live interp delay, with its `½rtt · tick · cushion` target decomposition inline), and the summed `Round trip you → you` (staleness of the authoritative world you react to — your own skater is predicted and feels instant). All info lines: each term is either by-design or health-colored elsewhere.

**Role-gated** — only the sections that apply to your role render, so you never read a misleading zero:

| Role | Detection | Sections shown |
|------|-----------|----------------|
| `SOLO (offline)` | `is_offline_mode` | local frame health only |
| `HOST` | `is_host && !is_offline_mode` | per-peer pings, client input queue, host frame health, upload bandwidth |
| `CLIENT` | otherwise | connection (RTT/loss/jitter/delay-spread), prediction/corrections, smoothing buffers, download bandwidth, watch metrics |

**Watch metrics** (client-only: stick jumps, puck hard-snaps, out-of-order drops, reconcile match) stay collapsed into a single `✓ Internals nominal` line and surface individually only when they leave the healthy band — they're the latent-bug tripwire. They are calibrated to **not** fire on normal play: "Stick jumps" counts only reconcile-induced blade teleports (fast stickhandling legitimately moves the blade >5 cm/tick and is no longer counted), and "Out-of-order drops" tolerates the occasional UDP reorder. The old "Prediction drift" line was removed — it measured the natural prediction lead (grows with RTT × speed), not a bug, so it cried wolf at speed; `reconcile_per_sec` + magnitude (Corrections) is the real divergence signal.

**The header verdict means "something is actually WRONG," not "your link is slow."** Only actual-problem metrics drive it (`_metric`): loss, Corrections, Guessing ahead, the watch tripwires, and host frame health. Connection **facts** — Ping/RTT, peer ping, Jitter, Delay spread — are colored for at-a-glance link quality but are **verdict-neutral** (`_context`): a far or jittery link is expected and the netcode compensates, so it shows red on its own line while the header stays green. The damage a bad link actually does surfaces through its own driving metrics (loss → rubber-banding, Guessing ahead → buffer overrun). So: glance at the header — green means nothing is wrong, even at 160 ms. Thresholds live in the overlay's health helpers and mirror the "Expected ranges" comments in `network_telemetry.gd` — keep the two in sync if either moves.

**`Jitter` vs `Delay spread` (the clumping tell):** `Jitter` is the p95 of raw packet *arrival-gap* deviation (IPDV) — it rises both for genuine path jitter and for relay **clumping** (several snapshots landing together, then a gap). `Delay spread` measures each packet's delay against the *synced host clock* (PDV — `estimated_host_time() − host_capture_time`, a de-clumped Jacobson EWMA of `mean + 4·dev` over a slow-rising floor), which clumping barely moves because each packet is timed against its own capture stamp. So: **`Jitter` high but `Delay spread` low ⇒ the link is clumping** (benign — packets just arrive early and fill the buffer), **both high ⇒ the path is genuinely jittery** and needs buffer depth. Read alongside `Packet spacing` (the arrival-gap histogram: bimodal low+high = clumping, a spread around ~8 ms = path jitter) for the full picture. `Delay spread` is not just a diagnostic — it **is** the jitter cushion in `Smoothing delay` (`rtt/2 + broadcast_interval + Delay spread`, at 1.0× since it already ignores clumping). The `Delay spread` floor also reads out the de-clumped one-way path delay (≈ RTT/2). **Canary:** `Guessing ahead` climbing on a clumpy link means the cushion is under-sizing — the revert (restore the `jitter_p95 × 2.0` cushion) is in the interpolation-delay invariant in `Scripts/networking/CLAUDE.md`.

### Playtesting telemetry (F4 markers + session collection)

F3 is a *live, local* diagnostic — only the player at that machine sees it, which is useless for remote playtesters. Two additions ship a tester's connection quality back for aggregation:

- **Always-on health dot** — `network_debug_overlay.gd` draws a small green/yellow/red `●` in the top-right at all times (the F3 verdict), so a tester notices a bad link without opening the panel. While the panel is closed the verdict is re-evaluated on a 2 Hz throttle (telemetry only refreshes at 1 Hz), avoiding the per-frame text build. The overlay also owns the optional FPS readout (Options → Video → Show FPS), rendered inline to the dot's left in a single top-right diagnostics row so the two can't overlap and the dot keeps one consistent corner spot; the row hides while the F3 panel is open (the panel carries the verdict and a Render FPS line).
- **F4 felt-lag marker** — any tester (exported builds included, unlike the dev-only sim keys) presses **F4** the instant something feels bad. It snapshots the live telemetry + in-session time and appends a marker via `NetworkSessionSummary.record_felt_lag`, plus a transient toast. Correlating *felt* badness with the objective numbers is the signal raw rates miss. Markers carry a **pre-history trace** (the ring of the last ~6 folded 1 s samples, `NetworkTelemetry.recent_samples` — the press lands *after* the felt moment, so the run-up matters more than the instant), attached to the first 8 markers; the hard size guarantee is `NetworkSessionSummary.to_dict_bounded`, which sheds marker detail (histories last-attached-first, then whole markers — never aggregates or counts) until the serialized payload clears the table's 64 KiB `pg_column_size` cap with compression headroom (the static marker caps alone couldn't bound it as the metric-key set grew — the first playtest's client rows 400'd on the constraint). **Auto markers** are the same mechanism fired by objective tripwires (`NetworkTelemetry._check_auto_markers`: hard-snap burst, reconcile storm, extrapolation, host stall, input starvation — thresholds mirror the F3 BAD bands) with a per-trigger 30 s cooldown + session cap, so rare bugs land with a timestamp and trace even when nobody reacted. The F3 panel's **C** key copies the whole session digest (same payload the reporter posts) to the clipboard, and every posted row is mirrored to `user://net_sessions/` (rolling 10) — testers can hand over their own data without a Supabase round-trip. `docs/telemetry_dictionary.md` is the interpretation key for all three.
- **Session collection → Supabase** — `NetworkSessionSummary` (`domain/state/`, pure, unit-tested) folds `NetworkTelemetry`'s per-second metrics into session-long **max / avg** (+ **min** for "lower is worse" metrics: sim rate, reconcile-match %, client fps, buffer depths; + **total** for `TOTAL_KEYS` rare-event counters — puck hard-snaps, blade jumps — where averaging would smear a handful of discrete events invisible), folded once per 1 s window in `NetworkTelemetry.tick` (GameManager refreshes live RTT/peer-count each frame for the fold to sample). `NetworkSessionReporter` (`game/`, mirrors `CareerStatsReporter`) POSTs one row per game — gated by the same offline/privacy checks plus a 30 s floor, flagging `net_sim_active` dev sessions. Two paths, one guard (`GameManager._report_net_session`): game-over posts `end_reason='completed'`; scene exit posts the abnormal ends the game-over path never saw (`quit` / `host_lost` / `host_ended` / `kicked`, reason staged in `NetworkManager.pending_session_end_reason`) — the sessions that end badly are the most diagnostic ones. Each row also carries **`game_id`** (the cross-peer match UUID career stats already use), so a match's host row joins its clients' rows — a rematch resets the summary (`NetworkTelemetry.reset_session` in `_apply_reset`) and re-arms the guard so each game posts exactly one row keyed to its own id. The evolving aggregate set rides in a `metrics` jsonb column (like `bug_reports.telemetry`) so adding a metric never needs an `ALTER TABLE`; only identity/filter fields are typed columns. Schema + analysis views in `supabase/migrations/*_network_sessions.sql`: `network_session_health` for "across all testers, what actually hurts," `match_health` for the per-game host+clients join (netcode failure modes are asymmetric — a host stall reads as client reconcile spikes — so they're only legible with both sides in one record). **`docs/telemetry_dictionary.md` is the interpretation key** (every metric's unit, healthy band, and failure meaning) — paste it alongside a row when handing session data to an LLM for diagnosis; keep it in sync when metrics or overlay thresholds move.

### Collision Layers

**Nothing in the game collides through the physics server.** Every actor
integrates its own motion and every contact — puck vs. geometry, skater vs.
skater, skater vs. boards / net / goalie, blade vs. puck — is solved analytically
in GDScript. No code runs a ray, shape, or overlap query, and every
`collision_mask` in the project is `0`. There are no composed masks left.

| Constant | Value | Tags |
|----------|-------|------|
| `LAYER_WALLS` | 1 | Tutorial / drill obstacle walls |
| `LAYER_GOALIE_STICK` | 4 | Goalie stick |
| `LAYER_GOALIE_BODIES` | 128 | Goalie pads / body / head / glove / blocker |

The **goalie is the only thing left with colliders**, and only because his parts
*are* the save geometry: `GoalieContactDetector` reads their shapes and
transforms directly. So a layer is an identity tag, not a filter — a NONZERO tag
marks a part live, which is how a disabled part is skipped. The rink, the nets,
the skaters and the puck carry nothing; the retired layers (blade `Area3D`s, the
puck `RigidBody3D`, the skater `CharacterBody3D`s, the boards, the net) went with
the nodes that carried them.

The rink and net colliders are worth a note, because deleting them was not purely
a cost decision: they were a *second, worse* copy of a boundary that already
exists. The perimeter was a 256-segment `ConcavePolygonShape3D` and the net a
stack of AABBs, while everything that actually reasons about those surfaces —
blade clamp, AI carom, puck-OOB, `Skater.clamp_body_to_rink` /
`clamp_body_to_net` — uses the smooth `GameRules` boundary. Two descriptions of
one wall, one of them read by nobody.

Keeping every actor out of the simulation is worth real host budget, not just
tidiness: a single active body or monitoring sensor switches on Jolt's per-step
pipeline for a fixed ~0.4 ms/tick (measured, 4-core) whether or not it collides
with anything. `Performance.PHYSICS_3D_ACTIVE_OBJECTS` should read 0 — the
network debug overlay surfaces it for exactly this reason.

## Decisions

**Authoritative host, no dedicated server.** One player hosts; the host runs all physics. Eliminates server costs and NAT complexity at the expense of host-advantage. Acceptable for a small-scale game like this.

**No pickup prediction for *contested* plays; visual-only optimistic attach for *uncontested* ones.** Authority and arbitration stay server-side — pickup is detected via lag-compensated rewind and only the grant confirmation travels to the client; carry state (`has_puck`, the shot state machine) never engages until that grant lands. The original blanket "no prediction" rule existed because rolling back a *contested* pickup feels worse than the round-trip. That objection is spatial: a pickup is only contestable when another skater is near the same puck. So `PuckController.try_provisional_pickup` pins the puck to the local blade immediately (visual only) when the pickup is **uncontested** — no other skater's blade within `contest_danger_radius` of the puck on the rendered view, puck grounded and below `pickup_max_speed` (a guaranteed catch, not a deflect), and not inside the post-loss reattach lockout. On the host's confirming `notify_local_pickup` the pin promotes seamlessly; on timeout (RTT-scaled deadline) or a different carrier it rolls back to interpolation. The contest gate keeps the rollback-prone case on the conservative round-trip path while making the common open-ice grab feel instant.

**Ghost mode over stoppages for offsides and icing.** Stoppages interrupt flow; ghost mode keeps the puck live and lets offending players correct their position. Downside: slightly less legible than a whistle. Acceptable for a game that prioritizes momentum.

**`_carrier_peer_id` managed by reliable RPCs, never world state.** Unreliable packets can arrive out of order relative to pickup/release RPCs, causing the puck to flicker between carried and loose. Reliable RPCs guarantee ordering; world state is ignored for carrier identity.

**Immediate physics snap, visual offset blend for the local player.** The body always sits at the authoritative position — gradual physics blending would create a window where the client is in a known-wrong position for collision/contact logic. Instead, `LocalController.reconcile` captures `pre_reconcile_visual_pos`, runs the input replay (which snaps the body to truth), then sets `skater.visual_offset = pre_reconcile_visual_pos - skater.global_position`. `Skater.visual_offset` (`skater.gd:154`) writes into `mesh_root.position` only, so the rendered mesh stays where it was on screen while the physics body has moved. Each physics frame `LocalController._physics_process` decays the offset by `_RECONCILE_VISUAL_ALPHA = 0.20` (≈88ms to 99% convergence). The game camera reads `global_position + visual_offset` so it tracks the smoothed visual rather than fighting the physics snap; `teleport_to` clears the offset so faceoff snaps don't carry residue. Remote players don't currently need this — they're interpolated between buffered snapshots, which is inherently smooth. If trajectory-style forward-prediction is ever extended to remote skaters, the same `Skater.visual_offset` mechanism is the natural place to hook in.

**The shooter's release rides the one predicted mode via a local-release seed (Phase 4b).** There is no separate trajectory-prediction mode: on a local release/nudge, `PuckController` stores a release seed (origin + velocity + `estimated_host_time()` stamp — the same client-sent origin the host fires from) and `_predict_loose` runs the shared analytic sim forward from the SEED instead of the newest snapshot, because every buffered snapshot still shows the puck carried until the host processes the release ~one-way later. The seed hands over to normal snapshot prediction on the first loose snapshot stamped at/after the seed — the shot-launch divergence probe measures exactly that seam — and a 0.5 s timeout is the deep-loss escape (stop trusting a shot the host may never have fired). Contacts need no special exit machinery: a goalie contact is the same prediction STOP as any predicted puck (hold at the contact — the save outcome is a host decision), frame bounces are the shared solver's own geometry, and the stateless re-predict folds the authoritative outcome in the moment its snapshot lands. No goal is ever predicted — the prediction loop parks an inbound puck on the goal line inside the posts (all pucks, not just the shooter's) and lets the horn arrive from the host.

**Goalie state transitions and shot reactions via reliable RPCs.** Interpolation gives smooth position but can't guarantee reaction timing — a butterfly during a rapid shot sequence may arrive in the wrong bracket order. Reliable RPCs deliver exact state changes; clients play a local reaction timer from the RPC payload for immediate visual feedback.

**Prediction residuals ride one smoother; only genuine divergence snaps.** The old three-zone trajectory reconcile (soft blend / velocity-only / hard-snap-and-exit, keyed on a full-RTT-projected broadcast) is gone with the trajectory mode itself: prediction is a stateless re-predict, so there is no explicit reconcile pass — each frame's target is recomputed from the newest authority and the residual lands in the velocity-feed-forward SmoothDamp tail. The only discrete decision left is the smoother's velocity-aware snap guard (`PuckHandoffRules.needs_hard_snap`): cross-track error at `_SMOOTH_SNAP_DIST` or along-track error beyond velocity × `_ALONG_SNAP_TIME_S` teleports (recorded as `puck_hard_snaps` telemetry when the target is moving — at-rest snaps are faceoff/goal-reset repositions and aren't counted); everything smaller damps out smoothly.

**Carrier transitions:**
- Pickup: client sends a reliable `receive_pickup_claim` RPC with `host_timestamp` and `interp_delay_ms`. Host rewinds `StateBufferManager` via `LagCompRewind`: blade at `self_view_time = host_timestamp + INPUT_LEAD_SEC` (the host snapshot whose blade reflects the client's locally-predicted view), puck at `puck_view_time = host_timestamp` (the claim stamp — the client renders the loose puck predicted at ~host present, so render == rewind at the stamp). Reads `blade_contact_world` (world-space mid-blade, host-only non-serialized field on `SkaterNetworkState`) from the rewound skater snapshot, runs the segment-segment distance test against the rewound puck path, and either grants the pickup, squirts the puck on a contested claim (two claims within 50ms, contest timer in `_physics_process`), or drops it as stale/invalid — **every no-grant outcome NACKs the claimant** (`notify_pickup_claim_rejected`, unreliable, v40) so their optimistic pin rolls back ~one-way after the reject instead of waiting out the RTT-scaled timeout (which stays as the lost-NACK fallback). **The host's present-time pickup tick arbitrates against a pending claim by stamp** (`PickupClaimResolver.arbitrate_present_grab`): a host-live grab (host player's blade, a remote's replayed one, a bot) no longer silently discards an in-window claim — stamps within `CONTEST_WINDOW_S` resolve as a genuine contested squirt (live kinematics vs the claimant's stored client blade), an older pending stamp wins the grant outright. On grant: reliable `notify_puck_picked_up` RPC to the carrier → `on_puck_picked_up_network()` on their LocalController + `notify_local_pickup(skater)` pins puck to blade. Simultaneously, reliable `notify_carrier_changed(peer_id)` broadcast to **all** peers so non-carrier clients drop loose-puck prediction for the carrier pin regardless of unreliable world-state delivery.
- Release: client predicts immediately (state machine transitions, the release seed arms loose-puck prediction) → reliable RPC to server to execute physics. Server fires `notify_carrier_changed(-1)` to all peers; a change TO loose leaves the shooter's release seed alone — the seed hands over on the snapshot timeline, not on the RPC.
- Poke check (strip): server detects opposing blade contact while `carrier != null` → clears carrier, launches puck via `_poke_check()` → `puck_stripped` signal → reliable RPC to victim client (`notify_puck_stolen`) → victim calls `on_puck_released_network()` + `notify_local_puck_dropped()` to clear carry state and drop back to interpolation.
- Goal scored: server captures carrier peer_id before `puck.drop()` → sends `notify_goal` (reliable, all peers) and `notify_puck_dropped` (reliable, carrier only) as separate RPCs → carrier client clears state in `on_carrier_puck_dropped()`; `puck.drop()` also fires `puck_released` → `notify_carrier_changed(-1)` broadcast. Decoupled so `notify_goal` isn't responsible for carrier cleanup.

`_carrier_peer_id` on clients is managed exclusively by `notify_local_pickup()` / `notify_local_release()` in `PuckController`. It is intentionally never updated from world state — unreliable packet ordering would cause it to conflict with locally-predicted transitions.

### Goalie Networking

**The goalie AI runs only on the host; clients are pure interpolators.** The host runs the full goalie state machine every physics tick. Clients do **not** run the AI — they buffer the host's broadcast goalie snapshots and render them at `now - interpolation_delay` via `GoalieController._interpolate_and_apply`, exactly like remote skaters and the loose puck. When `render_time` overshoots the newest snapshot, the root translation is dead-reckoned by the broadcast linear velocity (capped at `extrapolation_max_ms`) while the pose holds its newest value — a brief gap reads as a momentary freeze rather than wildly extrapolated sweep angles. This replaced the older "client runs the AI + soft position correction" model, which produced ghost saves and phantom goals whenever the client's local puck read disagreed with the host broadcast.

The full pose is on the wire, so the broadcast is the authoritative visual: butterfly drop, glove/blocker reach, RVH hug, and recovery all come straight from the interpolated host pose. Serialized per goalie (43 B quantized): root — position (x/z), rotation_y, state_enum, five_hole_openness, velocity (x/z); pose — body pitch/roll, each pad's offset + pitch/roll/yaw (pad yaw is the rebound-steering toe-out, on the wire since PROTOCOL_VERSION 13 so clients render the angled pads the host's rebounds play off), glove and blocker offsets + yaw/pitch, head yaw. `_apply_interpolated` sets `_sm.current` directly from the snapshot enum (body/head height lookups in `apply_network_pose` key off it, and debug/telemetry readers see the host's state), and adopts `five_hole_openness` from the snapshot. There is **no** client-side goalie AI tick, reaction state machine, or goalie state/reaction RPC. The host's only reaction signal, `GoalieShotReaction.started`, is host-internal — `_on_reaction_started` consumes it to arm the slide event-lockout, and it is never fanned out to clients.

Post integration triggers when `_is_puck_in_defensive_zone()` — either the puck is behind the goal line, or it is within `zone_post_z` of the goal line and the horizontal angle to the puck exceeds `rvh_early_angle` (default 80° — a true dead angle, on the conservative side of the modern "don't overuse RVH" teaching). The stance family then splits at the goal line (hysteresis `post_stance_swap_deadband_m`): puck behind it → **RVH** (ice seal for wraps/walkouts); puck in front at the sharp angle → **VH** (post pad vertical — keeps the short-side-high coverage RVH concedes). This matches the Buckley depth chart's "Defensive" corner zones, which extend slightly in front of the goal line at sharp angles.

**Tracking lag:** `GoalieController` maintains `_tracked_threat_position` that lerps toward the (puck-squared, lightly body-biased in tight) threat at a distance-scaled rate — `tracking_speed` (8.0) in tight fading to `tracking_speed_far` (3.0) at range, the quiet-eye smoothing that low-passes stickhandle jitter without squaring off the shooter's body. All positioning logic — lateral target, depth, facing, and state transitions — reads from this tracked position rather than the real puck. `_on_puck_released` (shot detection, server only) reads the real puck position and velocity so butterfly reactions stay accurate. (Goalie difficulty lives in `GoalieSkillProfile`, not this export.)

### Puck Interactions (server-side)

All puck contact logic runs on the host via `PuckController._check_interactions` each physics tick using swept-segment distance tests in `PuckInteractionRules`:

- **Segment-segment detection:** both `check_pickup` and `check_poke` use an Eberly analytical segment-segment minimum distance test. The puck is swept `puck_prev → puck_curr`; the blade is swept `blade_prev → blade_curr` (`blade_prev` captured at the start of `SkaterController._process_input`, *before* the per-tick IK update mutates `blade.position` — so the segment spans both the IK swing and the post-integration body motion). This catches fast blade swings through the pickup zone even when the puck is nearly stationary — the old static-blade test would miss those.
- **Catch vs deflect:** the puck's **receiver-relative** speed (puck velocity − skater velocity) against `deflect_min_speed` (default 22 — calibrated to real reception, ~49 mph closing; rationale + force math on `PuckReceptionRules.should_receive`), plus an `alignment_receive_bonus` that raises the ceiling (to 30 relative) only when the blade face is square to the *relative* approach line (hard contacts care about angle; passes don't). The relative frame is what makes a stretch pass to a streaking receiver easy, charging into a feed hard, and retreating with a shot a cushion — "give with the puck" as a skating read. Reception is **reactive** — relative speed and blade angle at contact, nothing else; there is still no blade-velocity / cushion term (it rewarded pre-loading a backswing, which felt fiddly and unintuitive — the skater's velocity is a frame correction, not a gesture). Below `pickup_max_speed` (relative) always catches. **Both detection paths run this decision:** present-time `_check_interactions` (live `skater.velocity`) and the lag-compensated `PickupClaimResolver` (which reconstructs `should_receive` from the rewound snapshot — puck and skater velocity off the snapshot, blade face normal from the buffered `blade_contact_world`/`top_hand_world`, so the verdict judges the closing speed the claimant saw at send time). The client's optimistic-pin gate (`try_provisional_pickup`) still reads *absolute* puck speed — safe because absolute + max sprint stays under the relative threshold, so "below `pickup_max_speed` ⇒ host grants" holds. The claim path used to grant possession on blade overlap *alone*, so a remote player reaching for a too-fast/poorly-angled puck caught it magnetically; now a deflect verdict routes to `PuckController.apply_lag_comp_deflect` (cooldown-guarded against a double-deflect with the present-time path) instead. `Skater.get_blade_face_normal` and the resolver share one definition via `PuckReceptionRules.blade_face_normal`.
- **Deliberate deflect (Q) + per-level reach and redirect:** `skater.deflect_intent` (set in `SkaterController._wants_deflect` = human holds the DEFLECT button `stick_lift`/Q without the puck; AI is exempt, overriding it to false) short-circuits the catch-vs-deflect decision and forces `apply_blade_deflect` — even an otherwise-catchable puck is tipped. The **loft level** (scroll, `skater.elevation_level`) shapes it via two coupled effects, neither a monotonic launch height (that would rocket a hard tip over the net):
  - **Reach** — the same `PuckReceptionRules.blade_can_interact(blade_up, puck_airborne)` gate as a passive receiver: `blade_up` already encodes the level's plane (grounded at FLAT/LOW, lifted only at HIGH), so FLAT/LOW play the ice (a saucer flies over) and HIGH plays the air (a grounded puck passes under). The level picks which plane you play; on the ice it also names the direction, in the air the geometry does.
  - **Redirect direction** (`PuckCollisionRules.deflect_loft_speed`, called from `Puck.apply_blade_deflect`) — the four loft levels are DEFLECT MODES that name the redirect's vertical sign outright: FLAT keeps a grounded puck flat, LOW lifts a grounded puck **up** (the money tip), MID lifts an airborne puck **up** (roof the rising shot), HIGH bats an airborne puck **down** (the net-front knockdown). The sign is the player's stated intent, never a `puck_y − blade_y` read — the old lifted-plane geometry (deadband and all) is retired, so identical contacts never flip outcome on a centimeter of height. Anti-degeneracy lives in the PIVOT heights instead: a LOW saucer apexes ~0.21 m, under even the MID pivot, so an air mode still only ever meets genuinely high pucks. The lift is a fixed **vertical launch speed** (`deflect_up_loft_speed` / `deflect_down_loft_speed`), not a fixed angle — it reuses the fixed-speed loft solve (`ShotMechanics.loft_y`), carving the lift out of the redirect's horizontal pace (energy-conserving, total speed unchanged). So the tip's **apex is consistent regardless of the incoming puck's pace** — a hard tip never sails over the net (a fixed *angle* would tie apex to pace², which is the sail-over bug; this is deliberately unlike the SHOT ladder, where the shooter owns the charge and the angle is the read).
  - **Blade lift** is a *consequence* of the deflect mode: `blade_up = (deflect_intent and level ≥ MID) or forced_lift`, and the lift TARGET follows the mode — MID rises to the low-air pivot (`blade_lift_height_mid`, ~0.35 m), HIGH (and the stick-lift / forced paths) to the full `blade_lift_height` (~0.52 m, reaching ~1.05 m — where net-front feeds arrive). FLAT/LOW keep the blade grounded so they meet pucks on the ice. The raised HIGH blade is also what hooks under a carrier's shaft, so **stick-lift is the same gesture** (Q held at HIGH near a carrier — the stick-lift path still gates on `blade_up`); the two mechanics share the HIGH lift height and pull it opposite ways (the deflect wants reach, `check_blade_under_stick` wants the blade below the victim's hands), which stays an open call.
  `deflect_intent` is a transient per-tick value derived from input (no replication / no snapshot — it recomputes from replayed inputs during reconcile), authoritative because the host runs `_process_input` for every skater it simulates. `LocalController` suppresses its speculative pickup claim + optimistic pin while the flag is set so the local player never predicts a catch the host will resolve as a deflect. (Moving deflect off the shoot button — it was `shoot_held` off-puck — also unmasks the human wrister one-timer, which the old deflect intent used to suppress.)
- **Deflect physics (bobble ↔ redirect from one model):** `PuckCollisionRules.deflect_velocity` decomposes the incoming velocity against the blade face normal (`Skater.get_blade_face_normal`, which points against the puck's travel) into a **normal** component (into the face) and a **tangential** component (sliding along it). The normal part rebounds with a restitution `e`; the tangential part is kept by `deflect_tangential_retain`. The two real outcomes fall out of this one decomposition, no angle cap needed:
  - a **square hit** (nearly all normal) off a hard puck → low `e` → the puck dies in front — a **bobble** (knocked down, not held);
  - a **glancing hit** (mostly tangential) → the glance survives → the puck keeps its pace and only its **line** changes — a true **tip / redirect**.
  `e` eases from `deflect_normal_restitution` (soft/slow puck) toward `deflect_normal_restitution_min` (hard puck, at/above `deflect_speed_ref`) so a squared blade smothers a slapper instead of caroming it; `deflect_tangential_retain` stays flat (a glance keeps pace at any speed). No angle cap is needed because the only way to reverse the puck is a square hit, and a square hard hit is killed by the low restitution — there is no fast carom to clamp. The loft level then adds a fixed vertical launch speed (unless the result is a dead-square knockdown, which stays flat): LOW/MID up, HIGH down, FLAT horizontal — see *Deliberate deflect* above. Deliberate and natural deflects share this one path.
- **Bobble as a recoverable outcome:** when the deflect result lands below `bobble_speed_threshold`, `apply_blade_deflect` treats it as a bobble — the deflector gets the short `bobble_cooldown` (gather your own knockdown) instead of the full `deflect_cooldown` lockout (which exists to stop re-touching a *live* redirect). The knocked-down puck is now slow, so the next contact resolves as a normal catch. Feedback (`GameManager` deflection cue) reads the same threshold off the replicated puck velocity, so a bobble sounds duller/quieter than a redirect identically on host and remote peers. The catch/deflect *decision* (`should_receive`) is unchanged — a bobble is a deflect-family outcome decided in the physics layer, so it stays "not a corral" and the contest-scan / prediction-rollback semantics are untouched.
- **Poke check:** when any opposing blade's sweep path passes within radius of the puck while `carrier != null`, `_poke_check` strips the puck (teammates cannot strip each other — gated by `PuckCollisionRules.can_poke_check`). Strip direction = `checker_blade_vel + carrier_blade_vel * poke_carrier_vel_blend` (or spatial direction as fallback). Ex-carrier gets `reattach_cooldown`; checker gets brief `poke_checker_cooldown`. Pokes are also lag-compensated via a client-claim path — see `PokeClaimResolver`. A checker mid body-check (`hit_committed`) or mid shot-block (`SHOT_BLOCKING`) is skipped: the stick is off the ice or committed flat to the block, so neither poke nor stick-lift fires. The block half of that is enforced on the present-time loop AND on both claim resolvers (judged from the rewound stance), since the client's own suppression is not an authority. Both detection paths run concurrently; idempotency guards on `PuckController.apply_lag_comp_poke` and the `puck.carrier != null` early-return in `_check_interactions` prevent double-strip.
- **Body check strip:** `SkaterController._on_body_checked_player` (server only) calls `puck.on_body_check(checker, victim, force, direction)`. If `force = weight × approach_speed ≥ body_check_strip_threshold` and `victim == carrier`, `_body_check_strip` clears the carrier and launches the puck in the hit direction. Emits `puck_stripped` + `puck_released` — same notification path as poke check. `Skater` also emits `body_check_impulse_applied(impulse)` with the total velocity delta from `_resolve_player_collisions()` each tick (attacker rebound + victim transfer from remote's check both included). `LocalController` connects to this signal and injects the complete delta into kinematic reconcile replay at the matching `host_timestamp`; the old `body_checked_player` approach captured only the attacker rebound, causing consistent under-correction and jitter. Body check VFX fires client-side from the sim — `SkaterVFX` connects to `body_checked_player` on every skater; no RPC needed.
- **Passive body block:** analytic, like every other puck contact — there is no `Area3D` and no `body_entered`. Each tick `PuckController._check_body_blocks` runs a **swept segment-vs-vertical-cylinder** test (`PuckInteractionRules.check_body_block`, so a fast puck can't tunnel through a torso) against every skater's body cylinder: radius `Skater.get_body_block_radius() + PUCK_COLLISION_RADIUS`, vertical extent `Skater.get_body_block_y_range()`. A hit calls `puck.on_body_block(blocker)` (host only), which reflects the puck off the body-center contact normal, multiplies speed by `body_block_dampen`, and sets a brief pickup cooldown on the blocker. Ghost skaters never block; knocked-down players still do; `body_block_cooldown` de-dups the level-triggered test. Only loose pucks deflect (`carrier == null`, plus a `pickup_locked` guard). **The vertical range is the mechanic:** the PASSIVE cylinder is raised to torso height so a grounded puck slips under or between the legs — that's what makes nutmegs possible — while the wider explicit shot block (Ctrl → `set_block_stance`, `block_body_radius`) rebases the cylinder to seal from the ice up to `block_seal_height`. Both block dimensions are the one-knee pose's: the extended leg and the flat stick earn the width, the kneeling head caps the height (so a shot lofted over a committed blocker gets through). The pose itself is cosmetic and lives in the gait (`SkaterSkatingCoordinator`) off the replicated shot state — the cylinder is the whole physical model, and `block_seal_height` is authored rather than read back from the pose because that pose advances at render rate.
- **Per-skater cooldowns:** `_cooldown_timers: Dictionary` (Skater → float). Cooldown only applies to loose-puck pickups/deflects, not to poke checks. Lets two players race a loose puck — only the ex-carrier has a disadvantage.
- **Stick tuck-in goals (front-of-mouth only):** you can score by carrying the puck across the goal line from the front — wraparounds / goalmouth jams — not just by shooting. The **net exclusion clamp** (`SkaterIKCoordinator.clamp_blade_from_net` → `NetClampRules.clamp_out_of_net`) treats the net as a solid box with only the **front mouth** open: a blade contact inside the box escapes through the nearest *solid* face, but a contact whose swept path (`prev → point`) entered through the mouth opening — the clear span between the post inner faces, `|x| < NET_HALF_WIDTH − POST_RADIUS`, under the bar — is left **unclamped** and confined to the mouth column, so it can ride in and out but never drift sideways through the posts / side netting. Front entry is gated by `allow_front` (passed as `_controller.has_puck`); follow-through and non-carry calls pass `false` and get the pure exclusion. Because the carry target *is* the (now-unclamped) blade contact, the puck-on-stick rides across the line, and `GameManager._check_goal_crossing` tracks **carried** pucks too (reseeding `prev` on the loose↔carried transition) so the tuck registers as a real crossing. **Back-entry stays impossible on both layers:** the net panels physically stop a puck from the back/side mesh, and `GoalDetectionRules.crossed_into_net` requires a front→back crossing, so a puck arriving from behind never scores. The goalie's body/butterfly blade clamp (`clamp_blade_from_goalies`) strips the blade on contact, so it defends the tuck lane.

### Why Not Predict Pickup?

Server-side collision detection + contested-claim arbitration is never predicted; only the **visual** attach on an **uncontested** grab is (`try_provisional_pickup` optimistic pin, with the carry state machine still waiting for the host grant so a rollback is at most a brief visual pop). Full gate detail in the "No pickup prediction…" decision above. **The contest resolution** (`PuckController.apply_contested_pickup` → `PuckCollisionRules.contested_pickup_velocity`) never awards possession — it squirts the puck free **biased toward the stronger blade's momentum** (vector sum of the two blade velocities, clamped; a true 50/50 pops perpendicular). Both entry points share it: the networked claim path (two claims within 50 ms) and the host present-time pickup tick, where `_find_contesting_corraller` detects a same-tick second corraller and routes it through the same call. So faceoff draws and board scrambles resolve identically. (Residual host/client asymmetry — the host commits present-time without holding for in-flight client claims — is unchanged; see the "cost of not adding a fixed pickup latency" note below.)

## Input Architecture

All input flows through an `InputState` data object populated by `LocalInputGatherer`. The abstraction supports swapping to network input or AI input without touching game logic.

`LocalInputGatherer` accumulates `just_pressed` events between physics ticks so no inputs are dropped. Mouse world position is computed via ray-plane intersection at y=0.

`InputState` carries the tick's `sequence`, movement, mouse world pos, and button/flag state (see the class for the field list).

## Blade Control

Blade placement goes through a custom top-hand inverse-kinematics solver (`TopHandIK.solve` in `domain/rules/top_hand_ik.gd`). The stick is a rigid rod of fixed length (`stick_length`, baseline 1.30 m). The `shoulder` marker anchors the top hand on the opposite side of the body from the blade (right shoulder for a left-handed shooter). The `top_hand` marker is the moving IK output.

**Blade-first feel:** The mouse world position is the desired blade target. The solver works backwards from the target: place the hand where it needs to be so the stick reaches, clamp the hand to an asymmetric ROM, then recompute the blade from the clamped hand along the aim line at `stick_horiz`. Whenever the target is reachable, blade lands exactly on it. When not, blade clips along the same aim line — angular aim is preserved, only distance drops.

**Asymmetric top-hand ROM (relative to shoulder):** reach caps are DERIVED from arm length in `SkaterController.apply_attributes` (so height scales them), not tuned independently — see the `_ROM_FOREHAND_OF_ARM` doc block.
- Forehand (cross-body) side: tight — `rom_forehand_reach_max` = arm × 0.5625 (≈ 0.39 m baseline), `rom_forehand_angle_max = 90°`. Hand stays near the body.
- Backhand (same-side as shoulder) side: open — `rom_backhand_reach_max` is chain-solved as `sqrt(arm_eff² − drop²)` with `arm_eff` = arm × `rom_arm_extension` and `drop` = `shoulder_height − hand_rest_y` (0.50 m × height mult — the whole chain scales with build height, so the derived reach does too; ≈ 0.46 m mesh-native), `rom_backhand_angle_max = 90°`. The chain solve guarantees no reachable hand target out-reaches the arm (the forearm never draws stretched) and supports one-handed backhand reaches.

**Vertical:** Blade Y stays locked at `blade_height`. Hand Y adapts: in the FAR regime (target past rest stick reach) it sits at `hand_rest_y`; in the CLOSE regime (target inside rest stick reach) it rises so `stick_horiz` matches the target distance and the blade lands on the target exactly. Capped by `hand_y_max` — past that the stick's min horizontal projection causes the blade to overshoot along the aim line.

**Arm rendering:** The shoulder and hand drive a 2-bone IK (`TwoBoneIK.solve_elbow`) that places the elbow on the plane perpendicular to the shoulder-hand axis in the pole direction (`arm_pole_local`, side-mirrored per arm). Both arms are ONE skinned mesh on ONE `Skeleton3D` (`Skater._build_arm_rig`), ten bones: upper arm and forearm per arm, elbow ball, gloved fist, and the wrist cuff ring. For those ten, surface index == bone index == `SkaterMeshBuilder.UpperBone`, so painting (`Skater.arm_part_material`), sizing (`set_arm_bone_radius` / `set_arm_ball_radius` / `set_arm_cuff_radius`) and posing (`_pose_arm_bone` / `_pose_arm_ball` / `_pose_arm_glove` / `_pose_arm_cuff`) all key off one number. Bones are flat (no parents) with identity rests and identity skin binds, and every vertex is weighted 1.0 to one bone, so a bone pose IS the local transform the part's node carried — the conversion is exact, not approximate. Radii scale with attribute visual bulk (`SkaterAppearanceCoordinator._apply_arm_thickness`; under attributes v4 all limb bulk rides the weight dial's frame bulk — silhouette = body), and the whole rig fades per-surface in ghost mode.

One trap this rig has to respect: **Godot skins normals with the bone matrix itself, not its inverse transpose**, so a non-uniform bone scale skews them. The arm bone's `(r, r, length)` is ~4:1, which is why `SkaterMeshBuilder._radial_side_normals` bakes the prism's side normals perpendicular to its axis — a normal with no axial component is invariant under that scale. The fix is only right where the anisotropy is *large*: it trades the taper's true normals for radial ones, and that trade only pays when the correct normal matrix was already flattening them (see the note on that function). The leg parts scale by roughly 1:1, so they keep their true normals and carry a small residual skew instead — measured, bounded, and documented in `docs/skinned-skater-plan.md`.

**Upper body:** the arm rig above IS the upper-body rig — the torso, the helmet/head unit and the two deltoid caps are four more bones on the same `Skeleton3D` and four more surfaces (five: the helmet contributes shell + head skin) of the same mesh. They join it rather than getting their own because they are siblings in `UpperBody`'s frame, so one skeleton means one pose array and no extra nodes at all. Their placement is read out of `Scenes/Skater.tscn` at `_ready` and the subtree freed, same as the legs. `set_head_angle` and `_orient_shoulder_cap` write bones; `SkaterMeshBuilder.apply()` is gone, since the skater no longer has a single mesh hanging on a node.

**On-ice HUD:** the slot rings, elevation chevrons and the slapper one-timer indicator are drawn by `Shaders/ice.gdshader` from uniforms fed by `IceRingField`, not by meshes. The slapper indicator is self-only, so it is scalar uniforms rather than an array — it was five nodes per skater (reticle, arrow root, arrow, gapped ring) plus an ArrayMesh rebuilt on convergence ticks, so that at most one skater could show it. Its geometry constants are mirrored in the shader; `SkaterHUDCoordinator` and `ice.gdshader` must be kept in sync. The stamina gauge followed. What is still a node is the self-beacon, which floats above the head and so cannot be an ice decal — and it is built LAZILY, only on the skater the ring-relation resolver reports as SELF, so exactly one exists in the scene rather than one per skater.

**Goalie rendering:** the goalie is deliberately NOT skinned — its moving parts are `StaticBody3D`s with live colliders, so bones would add per-frame writes rather than replace them (see `docs/skinned-skater-plan.md`). Its meshes are instead merged where they are rigid AND share a material: the catch glove (rim + pocket + cuff), the stick (shaft + paddle + blade) and the blocker (board + hand) are each one mesh on one node. The colliders in `Goalie.tscn` are untouched — the absorbed nodes were mesh-only.

**Leg rendering:** Both legs are one skinned mesh on one `Skeleton3D` (`Skater._build_leg_rig`), sixteen bones in the chain `LowerBody → Leg → Shin`, mirroring the node tree it replaced. Four pivots (`LegL/R`, `ShinL/R`) carry no geometry and exist to be rotated by the gait (`set_leg_swing`); the other twelve carry hips, thighs, knees, socks, skate collars and boots. Surfaces are `SkaterMeshBuilder.LegSurface` — twenty-two, not twelve, because the skate collar carries its accent stripe and the boot carries its toe cap, its blade holder, its steel runner and its laces. Each of those is a piece a gear MODEL paints on its own (`GearModelRegistry`); the runner is the exception that stays steel by construction. The segment offsets are **read out of `Scenes/Skater.tscn` at `_ready` and the subtree is then freed**, so the scene stays the place leg proportions are authored while costing nothing at runtime.

**Bottom hand (reactive):** A second hand grips the shaft a short way below the top hand. It is purely reactive — it never influences blade placement. After each top-hand solve, the controller computes the grip target as `top_hand.lerp(blade, bottom_hand_grip_fraction)` (default 0.25, ≈0.33 m down a 1.30 m shaft) and runs `BottomHandIK.solve` against an anchor at the `bottom_shoulder` marker (blade side of the body). The solver places the hand on the grip target unless the blade has swung into extreme backhand. Release is angle-based: the controller measures the blade's world direction in the skater's body frame, normalizes it so positive = backhand, and drives a smoothstep from `bh_release_angle_deg` (67°, matching the upper-body rotation clamp) to `+bh_release_angle_band_deg` (15°) — so the hand stays on the stick throughout any swing the upper body can track, and only blends to a shoulder rest pose when the blade genuinely passes the body's rotation limit. Rendered via the same `TwoBoneIK.solve_elbow` path with a mirrored pole. No network state is added — clients recompute the bottom hand locally from the interpolated top-hand + blade positions.

**Obstacle reach and the arm rebuild:** The boards are folded into the *reachable set*, not discovered after the solve. `SkaterIKCoordinator._board_reach_limit` casts from the shoulder along the aim line (`GameRules.ray_to_rink_inner`, sharing the boundary `clamp_to_rink_inner` projects onto) and feeds the distance to `TopHandIK` as `max_blade_reach`, which caps the desired blade distance *before* the CLOSE/FAR regime split — so a wall-limited reach lands in the CLOSE branch and chokes up (hand rises, stick tilts toward vertical) instead of solving full reach and being dragged back. Because the cap lands on the resolved target, every downstream consumer inherits it: the dangle speed cap, the wrister charge gate reading `last_target_blade_world`, the bots' scored release offsets.

Whatever the residual clamps (`clamp_blade_to_walls`, the goalie body/butterfly clamp, `NetClampRules`) still move, the blade is **authoritative** afterwards and the arm is rebuilt to reach it via `TopHandIK.hand_for_clamped_blade`. The priority is anatomical: the blade stays where gameplay put it, the arm stays inside ROM, and **stick length yields** — the hand slides down the shaft, the choke-up a real player does when jammed. Translating the hand rigidly with the blade (the older behavior, which preserved stick length) bounded nothing by the arm, so a board pin walked the hand behind the shoulder and folded the elbow through the torso, and a net reach threw it across the cage. The reconstruction is an exact inverse of `solve()` for any blade the solver itself placed, so nothing pops when a clamp starts or stops biting.

**Board shield:** A **carrier** within `board_shield_probe` of the boards has their facing target rotated away from the wall toward parallel (`BoardPlayRules`, capped at `board_shield_max_deg`, ramped by closeness, and never applied to a facing already pointing off the wall). This is the real pinned posture — square up along the boards and shield the puck — and turning parallel is also what genuinely lengthens the reach available along the wall. Facing does not drive locomotion (`input.move_vector` does), so this rotates the stance only; the torso still twists toward the cursor and the blade IK still tracks it. Gated to carrying: digging a loose puck out of the corner keeps full facing freedom.

**Facing:** The body's facing lazily tracks the cursor at `facing_drag_speed` at all times (so aiming past the angular ROM swings the target back into range), and freezes while the cursor sits in the unreachable wedge behind the skater (beyond `rom_backhand_angle_max_deg + upper_body_max_twist_deg` from forward) so the body never chases a target it can't reach — see `SkaterPoseCoordinator.apply_facing`.

**Upper body twist:** Rotates independently to express the angle between facing and blade direction (`upper_body_twist_ratio = 0.8`).

**Wall clamping:** The solved blade is projected onto the inner rink boundary (`GameRules.clamp_to_rink_inner`, testing heel *and* toe and taking the larger inward correction) before being written — the backstop behind the reach limit above, so it now corrects little more than toe overhang and the genuinely-jammed case where the boards sit inside the stick's minimum horizontal projection. If squeeze exceeds `wall_squeeze_threshold`, the puck releases *along the boards* in the carrier's travel direction (`ShotMechanics.wall_pin_release_direction` — the wall tangent, signed by carrier momentum, with a small `wall_pin_inward_bias` peel so it doesn't hug the boards), not straight out along the inward wall normal, so a puck lost on the wall dribbles down the boards instead of squirting into the slot.

**Network:** Both `blade_position` and `top_hand_position` are broadcast per world-state tick and interpolated on clients so remote players show a consistent stick pose.

## Shooting

**Puck carry speed penalty:** While carrying the puck, `effective_max_speed = max_speed * puck_carry_speed_multiplier` (default 0.85). The speed cap only applies to the cap check, not to thrust — so the skater still accelerates normally but is capped lower, preserving feel while making skating with the puck meaningfully slower than without it.

**Quick pass:** Press the quick-pass button (E). Fires a **blade→cursor** snap (from the puck's position toward the cursor, so it goes where you point) at `quick_pass_power` instantly from carry, no aim state. This is the **pass**, not a viable shot — `quick_pass_power` is flat pass speed for everyone. The button/action/input flag are all named `quick_pass*` (older history called it "quick shot"). Low skill floor.

**Wrister:** A **coil-and-release**. LMB-down enters `WRISTER_AIM`, which **FREEZES the blade+puck at the shot origin** (`SkaterController._apply_wrister_aim_blade` → `SkaterIKCoordinator.apply_blade_from_mouse(hold_blade=true)`): the puck sits still where it'll fire from while the upper body coils toward the cursor. Releasing fires **instantly** along **origin→cursor** — the *positional* aim (`_wrister_aim_dir`: `input.mouse_world_pos − SkaterAimingBehavior.wrister_origin_world`, the origin pinned at charge start and reconcile-restored), the same aim the quick pass uses. Power is the **pure mouse-speed model** (`ShotMechanics.wrister_power_t`): the raw screen-space cursor speed at release — EMA-smoothed (`cursor_speed_ema`), Shot-Power-Sensitivity-scaled (DPI-independent) — is the *whole* power signal; distance dragged does not enter. Forehand/backhand is the **cursor's** bearing-sweep chirality (`ShotMechanics.is_backhand_from_swing` over `swing_rotation`; the blade is frozen so the cursor is the only sweep). The blade-travel power **gate is DORMANT** — a frozen blade banks no `stroke_travel`, so `_wrister_stroke_travel` returns INF; the mechanism (`ShotMechanics.wrister_travel_cap_t`, `wrister_full_stroke_travel`, and `ChargeTracking`'s travel accumulation) is kept as the hook for a future cursor-sweep anti-degeneracy gate. `ChargeTracking` still accumulates the chirality + (unused) travel and fires the direction-variance reset. `shot_charge` carries normalized release-now power every tick (the goalie's pre-lean + the stick-flex pose read it); no on-screen charge ring. **Release → follow-through is the arm-controlled "whip"** (`SkaterShotPoseCoordinator._apply_wrister_whip`): the blade drives forward along the shot line *from the body* (`ShotMechanics.whip_local_dir` keeps it on the shot vector under any coil — never radial), on an attack-hold-release envelope; the torso through-overshoot is direct-driven (no lerp lag), facing re-squares hard (`follow_through_facing_recover_speed`), and the legs kick (`SkaterSkatingCoordinator`, powered by the release charge). **Bots** have no cursor, so they COMMIT their aim direction, hand, and power directly (`InputState.bot_wrister_aim_dir` / `bot_wrister_backhand` / `bot_wrister_power_t`, set in the agent's shoot/pass states — the exact shot the scorer evaluated); `_wrister_aim_dir` / `_wrister_is_backhand` use the commits for bots and positional/sweep for humans, and the bot's synthesized cursor is purely the cosmetic wind-up coil.

**Slapshot (with puck):** Hold right click. Blade fixes forehand, skater glides, upper body aims within `slapper_aim_arc`. Time-based charge, read diegetically: the wind-up pose (blade lift, torso coil) fills over the full `max_slapper_charge_time` (`SkaterController.slapper_wind_up_t`), so the animation is the charge gauge, with an apex quiver (`slapper_full_quiver_*`) as the full-charge tell.

**One-timer:** Hold right click without puck. Full movement available. Puck arriving while charging auto-transitions to slapshot state with charge carried over. Fires at the charge actually built (same timer as a normal release, plus `one_timer_center_power_bonus` for zone-center timing) — winding up early is what buys a full-power one-timer.

**Slapper aim is LOCKED at the press tick** (`SkaterController._enter_slapper_charge` → `SkaterStateMachine.locked_slapper_dir`) and never re-steers; every release path (`_release_slapper`, `_try_one_timer_release`, the charging goalie pre-lean) fires that frozen direction. Humans lock **blade→cursor** — from the squared blade-side release point toward where they point. **Bots COMMIT the direction** (`InputState.bot_slapper_aim_dir` → `ShotMechanics.slapper_aim_dir`, the same seam the wrister uses), because the blade anchor is a shoulder-anchored, attribute-scaled, facing-rotated offset ~1 m off the body that an agent can't reconstruct from a `WorldSnapshot` — and the bot's synthesized cursor sits only `CARRY_BLADE_AIM_FORWARD_M` (1.3 m) out, so subtracting the blade offset from it swung the locked line by tens of degrees. The one-timer is the *only* bot slapper (`ONE_TIMER_PRESSED`; `slap_pressed` elsewhere in the agent is the wrister-charge cancel), and it commits `release_point → aim_point` — the line from the settled slapper zone on the feed's live path, not from the body. The press itself is gated on the **stance**, not the blade cone (`ONE_TIMER_SQUARE_UP_MAX_RAD`, 45°): `_enter_slapper_charge` snaps facing to the aim, so a bot committing from a wide stance would whip its body around in one tick. A wide stance holds in `ONE_TIMER_PRESSED` with the cursor on the net, squares up at `facing_drag`, and presses when it lands inside — or bails to a catch at `ONE_TIMER_AIM_WAIT_MAX_TICKS`.

**Elevation:** Scroll steps the loft mode (0 flat / 1 low / 2 mid / 3 high). Persists until changed. Each level is a SET LAUNCH ANGLE from the blade curve's per-gear ladder (`ShotMechanics.shot_loft_y` over `PlayerAttributes._CURVE_LOFT_*_DEG` — design of record `docs/elevation-rework-plan.md` v3): charge controls pace, the level controls angle, arrival height is emergent from angle × charge × range and missing high is a real outcome. Quick passes keep the fixed vertical-speed table (`ShotMechanics.loft_y`) so the saucer and flip stay gear-free. The level is carried absolute in every input frame (2 bits, exactly 0..3), not as a sticky controller flag — reconcile replay re-derives it with nothing to snap. The levels double as deflect modes (see Puck Interactions).

## Bot AI

Bots run a per-tick **utility model**. The puck carrier scores every option — SHOOT, QUICK_PASS, PASS (per teammate), CARRY (per candidate spot), HOLD — in one expected-goals-shaped currency and takes the best; off-puck teammates score candidate positions the same way. The scoring is domain-pure and unit-tested (`Scripts/domain/ai/`, chiefly `action_scoring.gd`), driven by per-bot state machines (`Scripts/ai/skater_agent_state_machine.gd`) and a ~6 Hz positional slot assignment (`team_brain.gd`). Role behaviors — carrier, finisher, support, outlet, breakout, pressure, mark, contain, forecheck (F1–F3), chase, flank — live in `domain/ai/role_behaviors/`. **5v5 mode** branches the brain at one seam (`TeamBrain.team_size` → `role_slots_5v5.gd`'s position-gated group election; the 3v3 path is reused verbatim) and adds position-aware roles on the same dispatch rail: `zone_coverage.gd`/`zone_defense.gd` (hybrid D-zone with soft-lock), `defenseman.gd` (points / line pair / valve / back posts), `high_slot.gd`, `breakout_center.gd`, `wide_lane.gd`, plus the 5v5-gated transition-exposure term (`AIActionScoring.counter_rush_cost`) in the carrier's turnover price — design + researched tactics in `docs/5v5-ai-plan.md`. Goalies are separate (see the Goalies note in `CLAUDE.md`).

### Scoring philosophy — perception, not curves

Moved to `Scripts/domain/ai/CLAUDE.md`, alongside the difficulty-axis and
determinism rules, so it loads on demand when working in the AI layer.

### Bot-vs-bot duel harness

Emergent multi-second sequences — beating a container, escaping a pincer, blade-first retrieval — can't be pinned by single-dispatch unit tests, so `tests/unit/ai/duel_harness.gd` steps full headless duels between real bot brains: real `SkaterAgentStateMachine` dispatch + `TeamBrain` slotting, real `SkaterMovementRules.apply_movement` at 120 Hz, real `PuckInteractionRules` swept-segment pickups/strips; facing (exponential lerp) and blade (cursor-chasing, reach-clamped, rate-limited) are approximated, and body checks / stamina / boards / goalie behavior are absent (static home keepers exist only so shot scoring sees someone in net). A scripted **puppet container** (`add_puppet_container` — reaction-delayed P-control holding the puck→net line to a depth floor) stages patient containment deliberately, since a real lone defender chases. Scenarios (`test_bot_duels.gd`) assert coarse outcomes — possession kept, ground gained, an evade window fired — never trajectories; duels are deterministic under GUT (fixed RNG seeding), so outcomes are stable. A finding worth keeping: a carrier beats a *lone* defender with the committed cut + speed exactly as the clearance model prices it, so the fake-then-cut deke (home regime: slow jockeying, |closing| under the contain cap) fires rarely in open-ice duels — the deke's math/arming/lifecycle are pinned at unit level instead.

### Smart-ping obedience

A human's smart ping (see `CLAUDE.md` → *Smart ping*) reaches the bots as a **bounded tactical directive**, layered on the existing role architecture rather than bypassing it. Pipeline: the pinger's client resolves cursor context (`PingRules.resolve`, pure decision table) → vote-shaped reliable RPC (`NetworkManager.request_smart_ping` / `notify_smart_ping`, host self-fires so offline works) → `GameManager._on_smart_ping_received` shows the team-only bubble/marker and, host-side, elects the obeying bot (`PingRules.choose_obeyer` — a directed ping at a bot orders that bot; positional pings pick the nearest bot, never the carrier) and calls `TeamBrain.apply_ping`. Directives live in `AIPingDirectives` (one per pinger, ~3–6 s expiry on the brain's own clock, GUT-tested) and are consumed at three seams: slot/threat overrides applied after each brain tick (COVER_HIM = MARK + a pinned threat assignment, the house-pin shape; PRESSURE_CARRIER / GET_OPEN / DEFEND force their slots), per-bot queries read through `RoleContext` every dispatch (GO_THERE steering override, GET_PUCK chase override — which also replaces the chase election in `_enrich_snapshot_for_ai` and bypasses the race-lost decline), and carrier-scoring **biases** (`AIRoleCarrier.PING_SHOOT_EV_MULT` / `PING_PASS_EV_MULT`, ×3): a ping is an order, but the grounded models still veto a hopeless one — `FIRE_MIN_VALUE` keeps a pinged shot/pass from ever being a pure giveaway. The multipliers are legitimately hand-set *tactical* numbers (a human order, like the blue-line valve), not evaluation curves.

The only legitimately hand-set numbers in the AI are **feel / tactical tunables** — staging offsets, rush-speed thresholds, difficulty knobs, arrival tolerances — how the game should *play*, not how a situation is *evaluated*. When a bot behaves wrong, the fix is to give the model the perception it's missing, **not** to bolt on a corrective hack or a hard positional gate: a hack compensates for a model that isn't seeing something, and it rots. The finisher's old hard weak-side line — a reject-any-candidate-near-center clamp that existed only because the *previous* shot model undervalued the cross-seam, removed once the hole geometry valued it on its own — is the cautionary example. A magic curve in an evaluator is a model you haven't built yet.

## Physics

- **Engine:** Godot 4.6.2. Gameplay motion is **analytic**, not engine-simulated — the puck, skater bodies, skater-vs-skater contact, board caroms, the goal frame, and puck-vs-goalie all integrate and collide in our own deterministic code (see `docs/netcode-determinism-migration.md`). The physics server carries the collision *shapes* and nothing else; F3's "Physics 3D" active-body count is expected to read ~0.
- 120 Hz physics tick (Rocket League parity; the analytic puck step sub-steps near the goal frame — `PuckAuthorityRules.frame_substeps` — so a hard shot can't tunnel the pipes at this rate)
- **15 FPS host floor.** `max_physics_steps_per_frame` sits at Godot's default of 8 (P6 pinned it to 8 in `project.godot`, but 8 is the default so the editor strips it on save — it's a documented constraint, not a persisted setting). At the 120 Hz tick the host must render ≥ `120 / 8 = 15` FPS to keep physics real-time; below that, the sim dilates (slow-motion vs. the wall clock that clock-sync and broadcast cadence use) and every client interpolator extrapolates at once. Dropping the tick 240→120 Hz halved this floor (it was 30 FPS) and halved the per-tick host budget — per-actor allocation work and analytic-collision cost both scale with the rate. Raising the cap to tolerate even lower framerates risks a physics "spiral of death" (more catch-up steps make each frame slower still), so the floor is the deliberate failure mode. Keep the host comfortably above it via the per-tick perf budget; watch the F3 tick p95/p99 telemetry for transient dips (a GC hitch or heavy reconcile-replay frame can momentarily blow past it).
- Puck mass 0.17 kg, collision cylinder radius 0.065 m / height 0.035 m (oversized vs. a regulation 76 mm × 25 mm puck — a gameplay allowance; pickup/poke are center-based via `PICKUP_RADIUS`, so the collision size only affects physical bounces, fitting through goalie gaps, and the goal-mouth clearance in `GoalDetectionRules`, not corralling. `ice_height`/`PUCK_START_POS` track the cylinder half-height (0.0175) — update both if the height changes. `GameRules.PUCK_COLLISION_RADIUS`/`PUCK_COLLISION_HALF_HEIGHT` are the disc the analytic solver and the goal test sweep; the puck renders flat, so its horizontal reach 0.065 ≠ its vertical reach 0.0175, and both must stay in sync with the `Puck.tscn` mesh)
- `GameRules.ICE_FRICTION = 0.05` — realistic puck-on-ice μ, and the **single source of truth**: the analytic puck step and the AI/client trajectory model both read this one constant, so sim and model are the same number and can't drift. (An orphaned `Physics/ice.tres` once misled `ICE_FRICTION` to 0.1 while the live ice ran 0.01, which is why single-sourcing matters here.) `PUCK_BOARD_BOUNCE` / `PUCK_BOARD_FRICTION` are likewise authoritative. **There are no `PhysicsMaterial` resources left in the project at all** — the `Physics/` directory is gone. A material only ever fed the engine solver, and nothing reaches it: board, pipe, net, goalie-pad and goalie-stick feel are all numbers in `GameRules` / `GoalieSaveRules`, applied analytically. `GameRules.GRAVITY_M_S2 = 9.8` is pinned to Godot's un-overridden engine default (not textbook 9.81) by `tests/unit/rules/test_physics_constant_mirrors.gd`, so a project-setting override can't leave two gravities in the build.
- Puck velocity is clamped inside the shared analytic step (`PuckAuthorityRules` — host drive and client prediction alike), so every peer simulates from a sane speed.

## Game Flow

### Phase FSM

`GamePhase` is host-driven. Clients receive phase via reliable RPC on goal events and as a correction channel in every world state broadcast.

| Phase | Duration | Description |
|-------|----------|-------------|
| `PLAYING` | Until goal or clock expires | Normal gameplay; period clock counts down |
| `GOAL_CELEBRATION` | 1.5s (`GOAL_CELEBRATION_DURATION`) | Post-goal beat: movement allowed, puck pickup-locked; banner + VFX play |
| `GOAL_SCORED` | Replay length (2s `GOAL_PAUSE_DURATION` fallback if the replay never starts) | Goal replay cinematic; dead puck |
| `FACEOFF_PREP` | 2s (`FACEOFF_PREP_DURATION`) + skate-in extra / intro hold extensions | Skaters skate in to their dots (bench intro, staged post-goal, or from where play stopped), puck resets, goalies reset to crease |
| `FACEOFF` | Until pickup/touch or 10s timeout | Puck live at the dot, waiting for a player to engage it |
| `END_OF_PERIOD` | 20s (`INTERMISSION_DURATION`) | Period clock hit zero; skaters skate off to their benches, then the intermission band comes up — with the period's goals looping behind it when there are any (see *Period break presentation*) |
| `GAME_OVER` | Indefinite | All periods exhausted; movement locked until host resets |

Period clock (`GameRules.PERIOD_DURATION = 240s`, `NUM_PERIODS = 3`) ticks down only during `PLAYING`. When it expires: if periods remain → `END_OF_PERIOD` → `FACEOFF_PREP` (period increments, clock resets); if last period → `GAME_OVER`. `END_OF_PERIOD` and `GAME_OVER` are dead-puck phases.

**Period break presentation.** `END_OF_PERIOD` runs a skate-off: `PhaseCoordinator.on_period_break_entered` (host from `handle_phase_entered`; clients from the WS phase byte via `GameManager._on_remote_phase_changed`, idempotence-guarded) drives every skater to its bench door with the same `begin_approach` glide the faceoff skate-in uses — `SkaterController.tick_faceoff_approach` accepts approaches during `END_OF_PERIOD` as well as `FACEOFF_PREP` for this. The break arms the next prep as a **period-start bench intro**: the placement consumes the flag (pregame intro overrides it), starts everyone from `bench_start_position`, and host-extends the prep by `PERIOD_INTRO_DURATION` (the opening faceoff uses the longer `PREGAME_INTRO_DURATION` for its full-screen matchup rosters). `GameManager.period_break_started` (camera rises to the wide intro framing and holds) and `period_intro_started(period, duration)` (camera crane-down, HUD "2ND PERIOD"/"OVERTIME" card, crowd buzz) are the presentation signals; the upcoming period number is stashed at break entry (`period_after_break`) because a client's replicated `current_period` may not have advanced when the faceoff RPC lands. Goalies stay in/near the crease through the break (reset at prep entry as always).

**Intermission.** Every break is a fixed `INTERMISSION_DURATION` (20 s). `INTERMISSION_SETTLE` (2 s) after the horn — the chyron + skate-off beat, and the guarantee that every client holds the `END_OF_PERIOD` phase byte — every peer raises the intermission band (`GameManager._on_intermission_settle_elapsed` → `intermission_started`), and when the ended period has goals the host also starts a second `PostGameReplayDriver` instance configured looping + shared replay mode (`_start_intermission_replay`) over `GoalReplayStore.clips_for_period` (each clip is stamped with period + goal credit at capture). Replay mode freezes the host's SM tick, so the SM's `INTERMISSION_DURATION` timer only completes for a scoreless break; a reel break ends via the host's end timer — or a unanimous skip-vote (one host-owned tally scoped to the current skippable window — goal cinematic or break — cleared at window open; unanimity runs `GameManager._end_skip_window`, the drivers know nothing about votes) — stopping the reel, whose `reel_stopped` calls `GameStateMachine.finish_period_break()` to roll the next period's prep. Clients start/stop their own looping reel off the mirrored `notify_replay_mode` edge, branching on their replicated phase (`END_OF_PERIOD` → intermission reel, else goal cinematic). HUD presentation is `IntermissionOverlay` (light scrim + "END OF 1ST PERIOD" score band + per-clip goal captions + bottom-right break countdown over the skip line), driven by `GameManager.intermission_*` signals and dismissed by `intermission_ended` or the next prep announce (the reel-less path); Tab's box score still renders above it. Cosmetic companion: during the live skate-off a skater that reaches its bench door is hidden — "stepped off the ice" — by `GameManager._update_period_break_hiding` (position-derived on every peer, self-restoring on any phase/replay edge), so near-bench players don't stand frozen through the break.

### Goal Detection

Live goals are detected host-side by a **center-based swept goal-line crossing** (`GoalDetectionRules.crossed_into_net`), NOT an `Area3D` sensor. Each physics tick `GameManager._check_goal_crossing` feeds every `HockeyGoal` the puck's center segment (prev tick → this tick) — **loose or carried**, so a stick tuck-in from the front of the mouth scores (see the tuck-in note under Puck Interactions); the tracker reseeds `prev` on the loose↔carried transition so the pickup snap can't fabricate a crossing. `HockeyGoal.check_goal_crossing` returns a goal only when the puck **center** finishes crossing the goal-line plane this tick — ≥ a puck radius past the line, i.e. the *whole* disc across — travelling inward, with the interpolated crossing point inside a mouth **tightened by the puck's own extent** (`|x| ≤ POST_HALF_WIDTH − POST_RADIUS − PUCK_COLLISION_RADIUS ≈ 0.82`, `y ≤ NET_HEIGHT − POST_RADIUS − PUCK_COLLISION_HALF_HEIGHT ≈ 1.17`). `goal_scored` runs synchronously into `PhaseCoordinator.on_goal_scored_into`, flipping the phase out of `PLAYING`, so the check is ordered *before* the OOB / stuck-on-net checks — they then early-return rather than whistling the goal dead.

This replaced an `Area3D.body_entered` sensor that fired on shape-*edge* overlap from *any* face and never accounted for the puck's 0.065 m radius: a puck grazing the inside of a post (center ≈ 0.82 m — the sensor's exact overlap boundary) or entering the box from a side/back face scored on the weak `vel.z * facing > 0` gate ("phantom goals off the post / side of the net"). The swept center test rejects post grazes and side entries by construction and — being swept, not a fixed-depth volume — catches a fast shot that clears the whole goal depth in one 120 Hz tick, which the sensor could tunnel through. Detection is **loose-puck only** (a carried puck is pinned to the blade and can't fly in); drill/tutorial modes bail via `is_drill_mode()` (they own puck placement and run their own detection).

**Three detectors, one mouth.** Live play, penalty shots (`PenaltyShotRules.is_goal`), and the tutorial's plain-goal drills (`TutorialShotRules.crossed_goal_line`) all route their "between the posts, under the bar" test through the shared `GoalDetectionRules.point_in_mouth` — the post-centerline geometry stepped in by the pipe radius (`GameRules.NET_POST_RADIUS`) and tightened by the puck's extent (`PUCK_COLLISION_RADIUS` / `_HALF_HEIGHT`). So a post graze is not a goal in ANY mode, and the mouth can't drift between them. What stays per-mode is each detector's *lifecycle* around that test — live is a swept prev→curr whole-puck crossing on the host tick; penalty and tutorial are single-frame samples wrapped in their own dead-puck / target / wide-miss rules (penalty keeps its NHL 24.2 lost-momentum & backward rules, but keyed on the *shooter's* forward drive rather than the puck — dangling/shooting the puck can't fail the attempt, only the player stalling or backing off does; the tutorial's target drills still use the deliberately-lenient `nearest_target`, not the mouth). The depth "reached the line" test is also still per-mode (drills use center-past-line; live requires the whole disc across) — a negligible ~0.065 m difference for slow, every-frame-sampled drill pucks.

### Dead-Puck Enforcement

The `GameStateMachine` exposes `is_movement_locked()` — true during `GOAL_SCORED`, `FACEOFF_PREP`, `END_OF_PERIOD`, and `GAME_OVER`. `GameManager` re-exposes this as an instance method and is passed into each controller at `setup()` as the `game_state` dependency. Controllers call `_game_state.is_movement_locked()` every frame:
- `LocalController._physics_process`: zeros velocity, drains `_input_history`, skips input gathering and processing
- `RemoteController._drive_from_input`: still advances `last_processed_sequence` (keeps reconcile bookkeeping current) but zeros velocity and skips `_process_input`
- `LocalController.reconcile`: returns early during locked phases — `on_faceoff_positions` (reliable RPC) is the authoritative source of faceoff positions

### Controller API

`GameManager` describes *what* it wants; controllers implement *how*:
- `controller.teleport_to(pos)` — sets position, zeros velocity. `LocalController` override also clears `_input_history`.
- `controller.on_puck_released_network()` — idempotent; safe to call without checking `has_puck` first.

## Confusing Boundaries

**`GameStateMachine` vs `PhaseCoordinator` vs `GameManager`:** `GameStateMachine` is a domain `RefCounted` — pure state, no signals, no engine refs, lives on both host and client. `PhaseCoordinator` owns phase-entry side effects (puck lock, goalie reset, faceoff teleport), the goal pipeline, and the goal-replay cinematic (start/stop `GoalReplayDriver`, host-only state-machine advance on natural replay end); emits signals upward including `replay_started`/`replay_stopped`. `GameManager` owns `GoalReplayDriver` Node lifecycle (`add_child`/`queue_free`) and `ReplayFileWriter` lifecycle (open/close/rollover), but delegates cinematic driving to `PhaseCoordinator`. `GameManager` wires everything together and is the only one that **dispatches RPCs to / mutates state on** `NetworkManager`. Read-only timing queries (`estimated_host_time`, `get_latest_rtt_ms`, `is_clock_ready`, `estimated_input_stamp_time`) are an explicit exception — controllers call these directly so prediction / interpolation / input stamping can run without an orchestration hop. `LocalController.send_pickup_claim` is the one *write* exception: it dispatches an RPC directly because pickup-claim eligibility is checked on every physics tick and routing the call through GameManager would add a per-tick orchestration hop for a hot-path check. Do not extend this exception to other RPCs without revisiting the rule. `NetworkManager` holds no references to controllers: it pulls outbound input batches via a `Callable` provider set by GameManager (`set_input_batch_provider`), and emits `input_batch_received(peer_id, inputs)` for inbound batches which GameManager routes through `_registry`.

**`constants.gd` vs `game_rules.gd`:** `constants.gd` (autoload) holds engine-facing values: collision layers/masks, network port, input/state rates, physics tick. `game_rules.gd` (domain) holds game-rule values: rink geometry, icing duration, faceoff positions, ice friction.

**`WorldStateCodec`** is not a pure codec — it also emits `phase_changed` / `game_over_triggered` / `period_synced` / `clock_updated` / `shots_on_goal_changed` / `queue_depth_feedback` when decoding. GameManager connects to these so it can react to authoritative host updates on clients.

**`StateBufferManager`** lives in `Scripts/game/`, not `Scripts/networking/`. Host-only pre-allocated ring buffers (`PHYSICS_TICK × 3` slots = 3 s of history) for all actors. Owned by GameManager; WorldStateCodec reads `latest_*()` for broadcasts; lag-comp rewinds use `get_state_at()`.

**`GameManager` wires its RefCounted collaborators:** `PlayerRegistry`, `WorldStateCodec`, `ShotOnGoalTracker`, `HitTracker`, `TurnoverTracker`, `PossessionTracker`, `PhaseCoordinator`, `SlotSwapCoordinator`.

**Stat attribution keys off ESTABLISHED possession, not touches.** `PossessionTracker` (host-only, fed by the pickup/release/strip hooks; pure predicate in `PossessionRules`) declares possession established when the carrier holds the puck ≥ `ESTABLISH_HOLD_S` (0.75 s) or makes a deliberate play with it (pass/shot from carry — the `_start_pending_shot_from_carrier` hook). A momentary scramble attach establishes nothing. Consequences: takeaways/giveaways compute their candidate at pickup (`TurnoverRules` + the strip/shot windows) but **credit only when the recoverer establishes** — a board-scramble of alternating strips mints zero stats; faceoff wins go to the first team to **establish** after the drop (credited to that team's centre; stoppage fallback = last-toucher's team so every draw has a winner, and no turnover is charged while the draw is pending); the assist chain breaks only on opposing **established** possession (`ShotOnGoalTracker` records pickups as touches and upgrades on establishment — a puck thrown into traffic that nobody controls keeps the sender's assist); hit crediting is order-dependent (`HitTracker`): contact→strip within the window credits, contact→deliberate release **cancels** (they played through the check), release→contact within the grace credits (finished check). Stoppages flush everything: any phase transition out of live play (`_on_stoppage_flush_stat_trackers` — whistle prep, goal, period horn, game over) resolves a still-pending draw, kills pending hits + the release grace (a post-whistle shove is never a finished check; the release-grace arm is also phase-gated to `PLAYING` so the whistle's own puck drop can't re-arm it), and resets the possession model to neutral.

**`SkaterController`'s six `RefCounted` collaborators live in `Scripts/controllers/`, not `domain/`.** `SkaterStateMachine` (current shot state, follow-through timer, locked aim direction), `SkaterAimingBehavior` (wrister swing state — cursor-speed power signal + swing chirality — slapper charge timer, one-timer window), `SkaterPoseCoordinator` (facing, upper-body twist/lean, velocity lean, lower-body lag, head angle, angular-velocity bookkeeping), `SkaterShotPoseCoordinator` (slapper wind-up blade pose, wrister/slapper follow-through), `SkaterIKCoordinator` (mouse → top-hand IK, bottom-hand IK, net/goalie/butterfly clamps, blade-Y geometry helpers), and `SkaterSkatingCoordinator` (the procedural skating stride — velocity-derived gait with forward/backward/crossover blends, cadence saturation, glide-vs-push effort; purely cosmetic and derived from velocity alone, so remotes and replays animate identically with zero network state) all carry controller-local mutable state that is tightly coupled to per-tick input processing. Domain rules are stateless static methods; these classes are stateful collaborators owned by `SkaterController` and set up in its `setup()`. The pose and shot-pose coordinators expose public state fields (`facing`, `upper_body_angle`, `lower_body_lag`, `ik_locked_side`) so `LocalController.reconcile` can snap them on replay entry/exit; `_do_release` stays on the controller because it crosses multiple coordinator boundaries.

**Performance — shipped optimizations (rationale worth not regressing):**
- **~~Time-slice the carrier compete~~ — built.** The compete's steady-state re-eval now splits across two consecutive dispatches — FIRE phase (opponent lists, seam/protect/deke reads, pass-option cache, SHOOT + PASS scoring), then CARRY + commit against a fresh snapshot on the next dispatch (see the slice doc above `_commit_phase_pending` in `carrier.gd`). Commit cadence is unchanged (the post-commit cooldown is shortened by the dispatch the commit phase consumed); first-touch (reset), press-bail (clear_intent), and slow-dispatch-tier evals stay single-call. The feared duel-harness recalibration turned out to be a single throttle-contract test.
- **~~TeamBrain-shared threat memo~~ — built.** The brain publishes per-opponent `threat_surface_shoot` bases once per tick while any MARK slot is live (`TeamBrain.threat_shoot_base_by_opp` → `RoleContext`), and MARK's unassigned fallback consumes them as ordering/pruning bounds instead of recomputing per decide (micro: 352 → 238 µs, the `MARK (fallback, brain memo)` row). - **~~Far-play dispatch LOD + brain de-phase~~ — built; modest by measurement.** An OFF_PUCK bot beyond `FAR_PLAY_LOD_RADIUS_M` of the puck now runs the full dispatch shell (steering recompute, sprint resolver, role predicates) at half rate with an anti-lockstep parity offset — blade aim and cached-vector steering still re-step every physics tick, and the role-argmax cooldown drains by the real armed span so its documented cadences hold. - **~~Carry-candidate beam~~ — built (the first APPROXIMATE prune; every earlier prune was exact).** The compete's two-ply reads (pass option + carry continuation, ~90 % of a candidate's cost) now run only for the `CARRY_BEAM_WIDTH` (5) best one-ply candidates — pass 1 scores every candidate one-ply (a strict lower bound; the two-ply reads only raise a spot), pass 2 completes the best rows, best-first, under the old exact incumbent bounds (see the `CARRY_BEAM_WIDTH` doc in `carrier.gd`). This is a **search-budget policy**, not an evaluation-model change: a spot whose entire winning margin lives in the second ply can miss the beam. Measured (ai_micro): CARRIER compete (full) 1737 → 911 µs, open ice 2654 → 1368 µs — open ice was the worst case precisely because exact bounds can't prune when safety/lane ≈ 1 everywhere. A first cut that bounded pass 1 with the beam's K-th-best one-ply instead of the best REGRESSED contested play ~2× (weaker bound → ceiling prunes stopped firing) — the best-one-ply bound is exact for the argmax (a candidate whose ceiling can't beat the best lower bound can't out-upgrade it either), so there is no reason to ever use the weaker form.
- **~~Danger field~~ — built (`AIDangerField` + `score_shoot_threat_fielded`): the goalie-hole core of the THREAT-SURFACE family (`threat_surface_shoot` / `threat_local_shoot` / the turnover costs on them / the zone soft-lock read) is memoized on a per-net 0.75 m vertex grid, revalidated per vertex against the live goalie position (`GOALIE_EPS_M` — no TTL, no tick coupling), bilinear-sampled; the defender terms (lane, release contest) stay live per query so a hypothetical marker body still blocks exactly.** Serviceable for exactly this family because its core inputs are league constants + pure functions of position + the goalie's CURRENT spot; every predicted-keeper read (carry-candidate arrival shots, feed keepers, `counter_rush_cost`) deliberately stays exact — a current-position memo can't serve a hypothetical future goalie.
